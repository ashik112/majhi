## 1. What this is

majhi is a local, dockerized workspace where one developer runs AI coding agents for all of their work at once: their own projects, clients and teams, each kept apart as an org. It replaces opening separate CLIs (Claude Code, Codex) by hand. It is the owner's main daily tool, so speed, clarity and reliability matter more than feature count. The UI must be polished and fast enough to be a developer's daily driver: keyboard-first, dense where it helps, calm everywhere else.

The owner works on several orgs: their own projects, clients and teams. An org can come with its own Claude and Codex accounts, usually CLI subscriptions, sometimes API keys. An org can have several accounts of the same tool. More tools (OpenCode, Cursor, others) may be added later. Projects live under one or more workspace roots that the owner picks (for example `~/Work` and `~/private`). Repos are on GitHub, GitLab and Bitbucket, and the owner has SSH access to all of them. Trackers vary (Jira, ClickUp, GitHub Issues), but most tasks are local and never touch a tracker.

### Goals

1. Create a task in one sentence, with repos, base branch, agents, images, docs and links, and have an agent (or a team, when the owner picks one) do it in isolated git worktrees.
2. One task can span several repos. Each repo gets its own worktree, branch and MR.
3. Agents coordinate in a task room by @mentioning each other. The owner can talk to the room at any time.
4. Agents, accounts, models, skills and memory are fast to add, swap and configure. Models can be set by hand or picked per task by the decision provider. The owner has final say on every setting.
5. Work survives network loss and usage limits: runs pause at a checkpoint and resume, or hand off to another agent.
6. Token use is visible and minimized.
7. `docker compose up` gets it running in minutes.

### Non-goals (v1)

- Multi-user or team use. This is single-user.
- Cloud hosting. Local only.
- Replacing the git hosts' review UIs. majhi opens MRs and shows diffs, humans can still review on the host.
- Building our own agent. We drive existing agents over ACP.

### Principles

- **Own the core, reuse the parts.** majhi (orchestration, UI, data model) is ours. Protocols, CLIs and proven libraries are reused (section 4).
- **Files are the source of truth for config.** Agents, skills, org and project config live as plain files in `~/.majhi`, editable by hand and versionable. The database indexes and caches them.
- **Org boundary by default, owner override always.** An org's agents only see that org's work unless the owner explicitly allows otherwise. Root agents work anywhere, and can organize projects and create tasks, with owner approval for every change.
- **Nothing leaves the machine without approval.** No push, MR or merge unless the owner approves or the org's policy allows it.
- **Measure tokens.** Every run records token use. Optimizations are kept only if the numbers show they help.
- **One control plane, and the captain runs it.** Every change in majhi is a typed command. The UI, the palette and the captain agent all use the same commands, so the owner can set up and run everything just by talking to the captain (5.16). Everything is configurable at runtime, and every change can be undone.
- **No manual work outside majhi.** Anything the owner would otherwise do in a terminal, a config file or another app (loading SSH keys, restarting, mounting, signing in, fixing setup) is done by majhi itself, through the UI, the captain or the host helper. When something truly needs the owner outside majhi (answering a macOS prompt, finishing a browser sign-in, the very first `make up`), majhi says so explicitly, in the place the owner is looking, with the exact step. A terminal command is only ever a fallback, never the main path.
- **Light on resources.** Agent processes and models start when needed and stop when idle. Limits keep memory, CPU and tokens bounded (5.17).

### Workflow model (owner, 2026-10-19)

This section wins over anything below that disagrees, until each step of `docs/briefs/workflow-reset.md` rewrites the section it changes.

- **A task is one piece of work:** a short name, one agent by default, a plan inside it, and three lines its agent keeps current: Now, Next, Done when. A team only when the owner picks one on that task. Plan steps are not tasks.
- **One gate:** every path that creates or starts a task goes through one check. The owner's own tasks always pass. Others share a cap on running tasks (default 4) and a cap on open tasks per workspace (default 5); over it they wait or become ideas. A task an agent makes is an idea until the owner starts it.
- **Task model (built, step 1):** every task has a name (2 to 4 words) and, in a task its agent keeps current with `majhi-tasks.status`, Now, Next and Done when (120 characters each). One gate (`apps/server/src/tasks/gate.ts`) decides, for every creator, whether a new task starts, waits in line (`limits.tasks_running`, default 4) or is filed as an idea (`limits.open_by_others`, default 5 per workspace; always for agents and findings). Only the owner starts an idea. An agent starts only its own task and splits it into plan steps, never into tasks. The branch is `{type}/{name-slug}` and the folder `<tasks_dir>/<project>/<name-slug>`.
- **Teams (built, step 1b):** the only team is a lead and at most 3 workers, picked by the owner on a task. The lead writes a plan of at most 8 steps, each naming its owner; workers get work only from the plan, never by @mention; a step sent back twice stops and goes to Needs you. When an agent cannot run its step moves to the agent with the most headroom, a lead is replaced by the worker with the most headroom, and when none can run the task pauses with the exact fix and resumes by itself. An urgent start pauses the lowest-priority running task and it resumes through the line (5.3, 5.7).
- **The environment belongs to the project:** one builder and one package store per workspace, one environment (services, preview, dev database) per project with a queue, and a task is a branch and a worktree. A task that changes the schema gets a database copy dropped on close.
- **Three places:** Needs you (the only queue), Work (by workspace and project), Chat (captain, task rooms, client chats). Everything else is Settings. No new top-level page without the owner's yes.
- **Names say what and where:** a task shows as `project · Name` everywhere. Its branch and folder come from the name. The id is internal (address, tooltip, keys).
- **The captain runs a freelancer's operations:** incidents end to end, a morning brief and a weekly report per client, one authority level per workspace.

## 2. Core concepts

| Concept | Meaning |
|---|---|
| **Org** | A body of work kept apart from the rest: the owner's own projects, a client or a team. Has accounts, agents, projects, a default base branch, a tracker (optional), and a git commit identity. One org is built in: **Private** (id `private`, task key `PRV`), for the owner's own accounts and repos. It always exists, is the default when nothing else fits, and cannot be removed. Its entry in `majhi.yaml` appears only when the owner changes its settings. |
| **Account** | One login for one tool (Claude Code or Codex in v1), owned by an org, or by Private for the owner's own. Signs in either with the tool's own login (subscription) or with an API key. API-key accounts can carry extra fields the provider needs (a base URL for OpenRouter or a gateway, an org id, an Azure endpoint and deployment), with the same field kinds as connections (5.14). Has its own folder for its sign-in, and every workspace that uses it gets its own agent home (see 4.4). Usage limits belong to accounts. |
| **Agent** | A configured worker: role, account, model, instructions, skills, MCP tools, permissions, where it can work, and a fallback agent. Several agents can share one account. |
| **Root agent** | An agent with scope "anywhere", usually on a private account. Examples: Dispatcher (routes new tasks), Housekeeper (curates memory, cleans worktrees), Setup (scans the machine, drafts config, organizes projects). Root agents can create tasks and edit config, always with owner approval. |
| **Workspace root** | A folder the owner picks that holds projects, like `~/Work`. There can be several. majhi scans them for repos and mounts each one into the containers. |
| **Project** | A git repo under one of the workspace roots, belonging to one org. Has aliases used for parsing ("api", "web"), remotes, the remote used for MRs, and links to other projects. |
| **Task** | A unit of work. Local by default, optionally mirrored to a tracker. Has a kind (`code`, `ops` or `chat`, see 5.15), a brief, attachments, zero or more task repos, a team, a coordination mode and a status. Can have a parent task and depend on other tasks (5.4a). |
| **Task repo** | One repo inside a task: base branch, working branch, worktree path, MR, merge order. |
| **Room** | The task's conversation: owner messages, agent messages, and system events. |
| **Run** | One agent's ACP session working on a task. Has checkpoints and token usage. |
| **Memory** | Short facts with a scope (global, org, project) and provenance. Recalled into tasks. Curated with owner approval. |
| **Skill** | A folder with a SKILL.md in the Agent Skills format. Enabled per agent. |
| **Connection** | Access to an outside system: a Kubernetes cluster, New Relic, a mailbox, a server over SSH, a cloud CLI, any MCP server. Owned by one workspace or explicitly shared as Global. Workspace agents use their listed workspace connections and all Global connections; root agents can use all of them. See 5.14. |
| **Tool** | A kind of agent CLI majhi can drive over ACP (Claude Code, Codex). Each tool is one entry in a registry, so new tools are added without touching the rest of majhi. |
| **Decision provider** | An optional fast model that answers small typed questions (pick one, score, true or false) instead of writing text. Used for routing and model picking. See 5.12. |
| **Captain** | The one root agent the owner talks to for everything: setup, orgs, repos, agents, accounts, limits, tasks, debugging, stopping other agents. Which agent is the captain is itself a setting. See 5.16. |

### Task statuses

`inbox` → `ready` → `running` ⇄ `paused` → `review` → `mr` → `done`

- `paused` always carries a reason: `limit`, `offline`, `error`, or `owner`, plus the checkpoint to resume from.
- `review` means the team finished and the reviewer agent approved. The owner decides next.
- The task list groups these as: **Needs you** (review, paused, mr), **Working** (running), **Up next** (inbox, ready), **Done**.
- A task waiting on a dependency stays in **Up next** with a "Waiting on #12" chip. Waiting is derived from its links, not a separate status.

## 3. User experience

The UI reference is `design/ui-demo.dc.html`. It is a prototype written in a canvas component format, not production code. Reimplement it in React. Read its markup for layout and its `renderVals()` script for behavior and sample data. Where the prototype and this spec disagree (for example pause behavior or MCP tool names), this spec wins.

### 3.1 Main screen (one screen, three columns)

**Top bar:** app name, a command button that opens the palette (Cmd K), status pills (online state, teams working, accounts at limit, each clickable), and a Studio button.

**Left column: task box and task list**
- Task box: a multiline input. While typing, it parses the text live and shows chips for what it understood:
  - repos, matched by project aliases
  - never a base or working branch: words in the title or text are prose ("taken with Playwright", "work on main later", "the default branch"). The base is the project's, or the one picked for a repo on purpose (a project chip's branch, `repos[].base` on create); a picked base the repo does not have falls back to the project's with a warning. Until the task starts, its base can change (`tasks.update` with `base`). The working branch is always a new `{type}/{slug}` from the task's short name (DECISIONS 2026-10-08, no internal ids in client git)
  - @mentioned agents (these become the team; without any, the task has one agent)
  - links (fetched and given to the team)
  - attached files and pasted images
  - warnings: no repo found, or repos span more than one org
- Buttons: Attach, Save for later (status `inbox`), Start (creates worktrees and starts the team).
- Task list grouped as in section 2. Each row: org color, key, status, title, repos, team avatars.

**Middle column: task room**
- Header: key, org, status, title, repo chips (`repo: branch from base`), team avatars, and one primary action that changes with status:
  - review: "Approve, open N MRs" (plus "Send back")
  - mr: "Merge in order" or, if the org never lets majhi merge, "I merged it"
  - paused (limit): "Hand off to @fallback" (plus "Wait for reset")
  - running: "Pause"
  - inbox/ready: "Start team"
- Messages: owner messages right, agent messages left with agent handle plus account and model, system events centered. Attachments render as chips with type and a note about how they were used.
- Composer: attach, text input, send. Pasting an image or link attaches it. @mentioning an agent not in the team adds it to the room.

**Right column: tabs**
- Changes: per repo: diff stat, branch and base, worktree path, changed files, MR state. For multi-repo tasks, show merge order.
- Context: attachments given to the team, token receipt (brief size at start, recalled memory size, total in, cache hit rate, out), skills in play.
- Memory: facts learned in this task waiting for approval (Keep, Keep and add to AGENTS.md, Discard), and facts recalled for this task.
- Report (ops tasks): the task's `REPORT.md`, rendered, updating live as the agent writes it, with Copy and Send by mail (asks first).

### 3.2 Command palette (Cmd K)
Search tasks and memory, and run commands: new task, add account, new agent, install skill from link, search memory, swap an agent in the current task, resume paused runs, go to task, manage workspace roots. Keyboard-first.

### 3.3 Studio (one overlay, five tabs)
- **Agents:** list grouped by scope (Root, then each org), each with a status dot. Editor: role, where it can work, account (shows usage), model and effort (both read live from the account's agent over ACP, plus `auto`, which lets the decision provider pick), instructions, skills, permissions (edit files, run shell, push, open MRs, merge), MCP tools, fallback agent. Actions: New (per scope), Duplicate, Health check. Changes save to the agent's file immediately.
- **Accounts:** its own sidebar page (`/accounts`, `g u`), the one place to add, see, check, sign in again and remove every AI account, and see where it is used. Health and usage keeps the checks and the usage overview and links here. Org cards have an Add account button that opens the same flow with that org selected. Table with tool, org, "Used by" (the agents on the account, captain marked; from Phase 2 also the tasks running on it), current-window usage with reset time, weekly usage, status (healthy, running high, at limit, re-login soon, unreachable). API-key accounts show tokens and cost instead of windows. Add account flow: pick tool, pick org (Private is preselected unless the org filter or the only other org says otherwise), name is suggested (`claude-acme-2`), then either sign in through a device-code flow in an embedded terminal or paste an API key, then one click to create an agent on it. Selecting an account opens its details: status, last health check, usage, and "Used by" grouped by scope with each agent's role, model and effort. Agents that point at a missing account are listed so the broken reference is visible.
- **Memory:** search, scope filters (All, Global, each org, Needs review), rows with text, scope, source (task and agent), use count, and actions (Pin, To AGENTS.md, Forget).
- **Skills:** install from a GitHub link, skills registry name, zip, or local folder. Rows show source, which agents use it, and Enable for all / Remove from all.
- **Connections:** One list of every connection, grouped by how it connects (sign in with one click, sign in on this Mac, paste a token, needs your own app, your own servers and keys). Each row is one line: the service's mark, its name and account or host, the workspace or Global, one status lamp with its word and one line of why, how many agents use it, and one action (Check now, Fix, Reconnect). A side panel shows the status and the fix, what was checked and when, what agents can do with it, who shares it, its settings and Remove. Add connection opens a dialog that searches every supported service, grouped the same way, with the method and the time it takes, and runs the setup in place. Secrets are encrypted and entered once. Write access says what agents may change.

### 3.4 UX rules
- Every destructive or outbound action (push, open MR, merge, forget memory, move or rename a project, any write through a connection, sending mail) is explicit.
- Everything the Setup agent drafts is editable, and shows "Drafted by Setup" until the owner edits it.
- Keyboard shortcuts for the palette, new task, send, next/previous task, approve.
- Fast: task switching under 100 ms, room updates stream live.
- Dark theme first. IBM Plex Sans and IBM Plex Mono, as in the demo.
- Ids are for support, not for the owner: a chat shows its title, its agent, its workspace and when it was last active, never its task id (the id stays in the address and in a tooltip). One concept gets one place: the captain, its delegation, its log and its chat are one screen, the Captain page (5.18), not separate pages or tabs.

### 3.5 Workspace roots
Set during onboarding (3.6) and changed later from the palette or by the captain. The owner never types a path: a folder browser lists folders on the host (via the host helper, 4.2), marks git repos, and suggests likely roots (folders under home that hold repos, with their repo counts). Typing a path stays possible for keyboard users. Container mounts are fixed at start, so when a new root is saved, the host helper regenerates the mounts and restarts majhi on its own; the UI shows "Restarting to mount ~/X" and comes back with the new repos. Only when no host helper is connected does majhi show the `make up` command.

### 3.6 Onboarding
The first run is a short guided flow. Nothing else shows until it is done, and it can be reopened later from the palette.

1. **Workspace roots:** pick the folders that hold projects (3.5), from suggestions or the folder browser. majhi mounts them, scans them and shows what it found.
2. **First account:** add a Claude Code or Codex account, personal or for an org, by signing in through the embedded terminal or pasting an API key.
3. **Choose the captain:** pick the account, model and effort for the captain (5.16), or keep the suggested defaults. It is created as a root agent file the owner can edit later.
4. **Hand-off to the captain:** the captain opens its chat and finishes the setup as a conversation. It proposes orgs from the repos it found (remotes, folder names), asks one question at a time, adds more accounts and agents, sets limits, and registers projects. Everything it does follows the approval policy and can be undone.

Each step is one entry in a step list, so later phases add steps without redesigning the flow. The owner can skip ahead after step 3 and continue the setup with the captain at any time.

## 4. Architecture

### 4.1 Reused parts (do not rebuild these)

| Need | Use |
|---|---|
| Driving agents | **Agent Client Protocol (ACP)** over stdio, JSON-RPC. Use the official ACP TypeScript library (check the current package name at agentclientprotocol.com). |
| Claude | `@agentclientprotocol/claude-agent-acp` (the old `@zed-industries/claude-agent-acp` is deprecated) |
| Codex | `@agentclientprotocol/codex-acp` (replaces `@zed-industries/codex-acp`) |
| More agents later | The **ACP Registry** (agentclientprotocol.com/get-started/registry) lists ACP agents such as Cursor, OpenCode and Cline with install info. New tools are added from it. |
| Decision models | **Laya** (open weights, Apache 2.0), run locally: `laya-mlx` natively on Apple silicon Macs, `laya` (PyTorch) in Docker everywhere else. **TypeSafe Jev** (hosted API, needs a key), optional. An ACP agent can stand in for either. See 5.12. |
| Skills | Agent Skills format (SKILL.md). Install with the open `skills` CLI (`npx skills add ...`). |
| Semantic code tools | **Serena** MCP server (LSP-based symbol lookup and editing) |
| GitHub | `gh` CLI |
| GitLab | `glab` CLI |
| Bitbucket | Bitbucket Cloud REST API |
| Jira, ClickUp | Their REST APIs (or official MCP servers if they cover what we need) |
| Git worktrees | `git worktree` via a thin wrapper |
| Web terminal for logins | `xterm.js` + `node-pty` |
| Command palette | `cmdk` |
| Diff view | `@git-diff-view/react` or Monaco diff editor, pick one in Phase 4 and log it |

Verify each package name and version before installing. Several of these moved fast in 2026.

### 4.2 Services

```
docker compose
├── server     TypeScript backend (Node 22), HTTP + WebSocket, SQLite
│              owns: config, tasks, rooms, routing, memory, MCP server for agents
├── web        React app (Vite build, served by the server in production)
├── runner     image with agent CLIs + ACP adapters + gh + glab + git + Serena
│              + language servers + kubectl and other connection CLIs;
│              the server spawns agent processes here
└── laya       local Laya decision model (Python, PyTorch on the CPU or an
               NVIDIA GPU), behind a compose profile; used on Linux, Windows
               and Intel Macs, and as the fallback on Apple silicon; see 5.12

host helper   `apps/host`, a small Node process on the owner's computer (not
              in Docker), installed by `make up` as a login service: a macOS
              LaunchAgent, or systemd user units on Linux and WSL2 (the table
              below has what differs per OS). It opens no port: it long-polls
              the server over the published 127.0.0.1 port with a token from
              `~/.majhi/host.token`, and does only fixed jobs: list host
              folders, suggest roots, remount roots, keep the SSH agent loaded
              (below), and give a key's passphrase to `ssh-add` once
              (`ssh.unlock`; the passphrase travels browser, server, helper
              over localhost, is never logged by majhi, and only the OS
              keyring keeps it).
              SSH keys: at start (login), after a wake from sleep, when a
              fetch fails for lack of SSH access, and on `ssh.reload` it loads
              the keys whose passphrase the keyring keeps, then every private
              key from `~/.ssh/config` `IdentityFile` entries and the default
              names that has no passphrase and is not loaded yet, and reports
              the count and the keys that still need a passphrase.
              Ops jobs (Phase 2b): it reports the checkout's HEAD, whether it
              has uncommitted changes and which Docker runtime is in use in
              its poll header; `version.changes` answers with the commit
              subjects between the running image's commit and HEAD (`git log
              --format=%s running..HEAD -n 20`); `update` rebuilds and
              restarts majhi (below); `restart` exits so the login service
              starts it again. At start (login) it makes sure Docker is up
              (starting it where it can, waiting up to 2 minutes, polling
              every 5 s) and that majhi is running (`docker compose up -d
              --wait` in the checkout when its container is not), logs each
              step, retries a failed start twice a minute apart, and only then
              posts a notification with the one step the owner must take.
              `update`: `docker compose build` with the same environment as
              `make up` (HOST_UID, HOST_GID, HOME, MAJHI_COMMIT from `git
              rev-parse HEAD`, and the agent socket and Laya GPU `make up`
              picked), create the secrets key if missing, regenerate the
              override, `up -d --wait`, copy the helper bundle out of the new
              image over `~/.majhi/bin`, then exit so the login service starts
              the new helper. Progress goes to `~/.majhi/update.json` (the
              server that would relay it is replaced part-way); the UI reads
              it through `system.version` and reloads when `/health` reports
              the new commit.
              On a release install (install.sh: `.env` has MAJHI_VERSION and
              MAJHI_LATEST_URL) the helper asks the latest-release pointer at
              most every 6 hours and reports that release's commit instead of
              HEAD; `update` first moves the checkout and MAJHI_VERSION to
              that release, and the same `docker compose build` then takes the
              release images from ghcr.io instead of compiling. A failed update
              puts the checkout and `.env` back with the previous images.
              On Apple silicon it also runs Laya natively with `laya-mlx`
              (MLX on the GPU). Later it is also where MAJHI_RUNNER=native
              spawns agents.
```

### 4.3 Stack

- Monorepo: pnpm workspaces. Packages: `apps/server`, `apps/web`, `packages/shared` (types, zod schemas), `packages/acp` (ACP client wrapper), `packages/mcp` (majhi's MCP tools for agents).
- Backend: Node 22, TypeScript strict, Hono, `ws` for WebSocket, Drizzle ORM over `better-sqlite3` (WAL mode). No Redis. A persisted jobs table handles background work.
- Frontend: React 19, Vite, TanStack Router and Query, Tailwind, shadcn/ui, Zustand for local UI state.
- Validation: zod everywhere at boundaries.
- Tests: Vitest (unit, integration), Playwright (end to end).
- Lint/format: Biome.
- Images: one multi-stage `Dockerfile` for the server and the runner (4.5, "Lean images"). Downloads, package managers and their caches stay in build stages; each pinned version has one home.

### 4.4 Files on disk

```
~/.majhi/
├── majhi.yaml                 workspace roots, orgs, accounts, projects, aliases, links, policies, defaults
├── agents/<id>.md           one agent per file: YAML frontmatter + instructions body
├── skills/<name>/SKILL.md   installed skills (Agent Skills format), with skills-lock.json beside them (5.2)
├── accounts/<id>/           each account's sign-in file, who it is pinned to, and what probes and usage reads write; no run mounts it
├── agent-homes/<org>/<account>/  the home of one workspace on one account: HOME and the CLI's config home of its sessions (`_majhi` is the home of sessions that belong to no workspace)
├── memory/memory.db         memory store
├── majhi.db                   tasks, rooms, runs, usage, index of the files above
├── cache/<org>/             one shared package store per workspace (pnpm-store, npm, yarn, pip); ignored by history, not backed up
├── secrets.age              tracker tokens and API keys, encrypted with age
└── .git/                    config history: every change is a commit, so it can be undone (5.16)

<tasks_dir>/<task-id>/       one folder per task (default: <first workspace root>/.majhi)
├── TASK.md                  generated brief (see 5.4)
├── AGENTS.md, CLAUDE.md     generated, point to TASK.md
├── attachments/             images, docs, fetched link content
└── <repo-short>/            one git worktree per task repo
```

An agent session's `HOME` and its CLI's config home are both its workspace's home on its account, `agent-homes/<org>/<account>`, so what an agent writes there (settings, hooks, MCP servers, instructions, transcripts) reaches that workspace's next sessions and no other workspace's. A session with no workspace (the captain across all workspaces, a job with no org, the decisions stand-in) uses `agent-homes/_majhi/<account>`, and a task with no org uses the Private workspace's. A new home is seeded with only who the account is (`oauthAccount`, `userID` and `hasCompletedOnboarding` of Claude's `.claude.json`). The sign-in file (`auth.json` for Codex, `.credentials.json` for Claude) is the one file shared across workspaces: a runner bind-mounts it from the account's folder into the home, because the CLI rewrites it in place when it refreshes a token and refresh tokens rotate, so copies would sign each other out. Next to majhi (`MAJHI_RUNNER=local`, tests and development) agents are not isolated, so the account folder stays the home. Majhi pins each login account to the person who signed in and refuses to start a session on a sign-in file that belongs to someone else (the account then shows as signed out in Needs you, with the reason).

### 4.5 Docker details

- The image bakes the git commit it was built from (`ARG MAJHI_COMMIT`, exposed as the env var `MAJHI_COMMIT`, `dev` when unknown). `make up` and the host helper pass `git rev-parse HEAD`. `/health` reports it, so a browser can tell the new server from the old one after an update. Building never needs the owner: `docker compose build` reads the same variables `scripts/up.sh` exports (`make up` and install.sh both run it). Where the images come from is one rule: with `MAJHI_VERSION` in `.env` the server, runner and Laya images are that release's, pulled from `ghcr.io/ashik112/majhi-*:<version>` (Laya `-cuda` with an NVIDIA GPU), and only the last stage, the owner's passwd entry (`docker/owner.sh`), is built locally; without it every stage is built from the checkout. Either way compose tags the result `majhi-*:dev`. Releases are automatic: on every push to main, `.github/workflows/release.yml` works out the next version from the conventional commits since the last release (`scripts/next-version.sh`: breaking change major, `feat` minor, `fix` or `perf` patch, nothing else releases), builds the images for amd64 and arm64, and only once every image is pushed creates the tag and the GitHub release and marks it latest. That latest release is the one pointer install.sh and the host helper read. Docker access: macOS asks once whether OrbStack or Docker Desktop may read `~/Documents`, `~/Desktop`, `~/Downloads` and iCloud Drive; without a yes the container sees an empty folder, so the roots screen warns before saving a root there and names the runtime the helper found.
- **Lean images** (workflow reset step 2b). Three images are assembled from stages: server, runner and browser. Every download, `npm`, `uv` and `apt` cache lives in a stage that is not the last of a chain, and the final stages hold only runtime files (`COPY --from` of the browser, the Python tools and the server's native libraries, and one apt layer with no recommends and no docs, man pages or locales). Server and runner start from one `base` stage (Node, git, gh, glab), so those layers are on disk once. The agent CLIs (the two ACP adapters with their native binaries) are in the runner only: sign-in, the CLI version, the sign-in status, the model probe and the usage read each run in a short-lived runner container that mounts only that account's home (`packages/acp/src/tool-process.ts`), so the server image carries no agent CLI. Versions used by more than one stage are `ARG`s at the top of the `Dockerfile`; the server's native libraries take their versions from `apps/server/package.json`. A code-only update adds only the server's `dist`, `web` and `host` layers (about 40 MB). Sizes (arm64, `docker images`): runner 2.76 GB (was 5.62), server 0.94 GB (was 2.21), browser 1.12 GB (new); compressed, 0.68, 0.23 and 0.32 GB. What each remaining MB is for is in `docs/DECISIONS.md` ("Lean images").
- **Browser container** (workflow reset step 2b). Chromium is not in the runner. A browser connection (5.14) of a workspace runs in that workspace's own browser container, `majhi-browser-<workspace>`, from the browser image, on a network of its own (`majhi-browser-<workspace>`, a /24 of `10.211.0.0/16`), both named and labelled by `apps/server/src/containers/names.ts` (`browserNames`). The server starts it when a run of the workspace first needs the connection, and the container ends itself after 15 minutes without a client (its Chromium after 5); a workspace with no browser run never starts one. It mounts only the profile folders of that workspace's browser connections, so one workspace's logins are never in another's browser, and a container is never shared across workspaces. It starts through `majhi-netguard` like a runner (private networks closed, owner's uid, no capabilities, no new privileges), and the Docker socket is not in it. A run that holds the connection joins the browser network, and its guard opens that one address (`<ip>/32`) and nothing else on it. Playwright MCP attaches over CDP (`--cdp-endpoint`) and Chrome DevTools MCP with `--browserUrl`; `docker/browserd.mjs` is the container's only process: it answers CDP discovery with the caller's address, starts Chromium on a profile's first connection and stops it when idle. Without a runner (tests, development) the MCP server starts its own browser as before. A connection of no workspace has no browser container and is not offered to runs.
- **Test browser** (a repo's own `playwright test` in a task). The runner has no browser, so a run gets a Playwright server instead: the `majhi-testbrowser` image (Chromium and its headless shell, the system libraries and `playwright-core` at majhi's own pin, 1.53 GB unpacked, 0.44 GB compressed), one container per workspace (`majhi-testbrowser-<workspace>`, named and labelled by `testBrowserNames` in `containers/names.ts`), started when a test first connects and ended by its own timer (its server after 5 idle minutes, the container after 15 without a client). Every run (and every hand-off check) of a container-mode majhi gets three variables, with no change to the repo: `PW_TEST_CONNECT_WS_ENDPOINT` (`ws://<majhi>/mcp/testbrowser`), `PW_TEST_CONNECT_HEADERS` (the run's own bearer token) and `PW_TEST_CONNECT_EXPOSE_NETWORK=<loopback>`, so an unmodified `npx playwright test` connects to majhi, and the page it drives can still open the run's own `localhost` (the `webServer` of the repo's config). majhi finds the run's workspace from the token (never from the request), starts that workspace's container on the runner network if it is not running, strips the token and passes the WebSocket on. A runner cannot reach a test browser directly (the guard refuses private networks), so the only way in is that authenticated route, and a container never serves another workspace. The container starts through `majhi-netguard` (public internet only, owner's uid, no capabilities, no new privileges), mounts no folder of the computer, and has no Docker socket. `docker/testbrowserd.mjs` is its only process: Playwright's client and server must be the same major.minor, and the client says which in its User-Agent, so it starts `playwright-core run-server` of that exact version on the first connection, the image's own version at once and any other version installed first into the container (about 50 s the first time). Only Chromium is installed: a test that asks for Firefox or WebKit gets Playwright's own "not installed" error.
- `health.run` runs the same checks as `make doctor` (config, config folder, git, each root mounted, tasks folder, host helper, SSH agent, each git host, secrets key, each CLI version, each account from its cached health, disk space). Each failed check that majhi can fix carries a `fix` label and `health.fix` runs it: mount a root (helper remount), create a missing folder, reload SSH keys, check an account again, open an account's sign-in (the UI opens the terminal), restart the helper. A failed check with no fix says the exact step in plain words.
- Bind mount each workspace root at the **same absolute path** inside the containers, so paths match between host, agents and the owner's editor. `docker compose` cannot loop over a list, so majhi generates `docker-compose.override.yml` with one mount per root from `majhi.yaml`. The host helper regenerates it and recreates the server container whenever roots change; `make up` does the same on first start. Only roots are mounted, never the whole home folder, so agents cannot reach other credentials in it.
- Docker per OS: OrbStack or Docker Desktop on macOS, Docker Engine run as root on Linux, Docker Desktop with WSL integration on WSL2. `make up` refuses Docker Desktop for Linux and rootless Docker for now: both map container uids through a user namespace, so the owner's uid in the server lands on another uid outside, and worktrees and `~/.majhi` would stop belonging to the owner.
- Mount `~/.ssh/config` and `known_hosts` read-only. Forward an SSH agent from the host to majhi's own git only (fetching the base when a task starts, pushing after approval). The generated override adds it from `MAJHI_SSH_AGENT`, which `make up` sets per OS and the host helper keeps for remounts and updates: on macOS `/run/host-services/ssh-auth.sock`, the Mac's agent as OrbStack and Docker Desktop give it to containers, mounted at `/run/ssh-agent.sock`; on Linux and WSL2 `~/.majhi/run/ssh-agent.sock`, the host helper's forwarder (4.2), which the server already sees through the `~/.majhi` mount, so only `SSH_AUTH_SOCK` is set and the path stays the same when the agent behind it restarts; any other absolute path is mounted at `/run/ssh-agent.sock`; `off` gives none. It is never forwarded to agent runs: agents have no SSH access, which also closes the push-by-script gap in the push check, and the runner isolation check makes sure a runner cannot see `~/.majhi/run`. Private keys never enter the container. Only the **public** keys (`<IdentityFile>.pub` for every `IdentityFile` in `~/.ssh/config` and the default names, when the file exists) are bind-mounted read-only at their host paths, in the generated override next to the roots: with `IdentitiesOnly yes` OpenSSH reads the `.pub` file to choose the matching agent key when the private file is missing. A mount source without the `.pub` suffix is refused. The image's last stage adds a passwd entry for the owner's uid (home = the host home), built on the owner's computer, because ssh will not run without one. `doctor` runs `ssh -T -o BatchMode=yes -o ConnectTimeout=5` against each ssh alias or `user@host` used by a registered project's remotes and reports reachable, auth failed or unreachable; `host.status` carries the same result (`sshHosts`) and Repos names a host that took no key. The host helper keeps the agent loaded (4.2); a key with a passphrase is unlocked once from the Repos screen and kept by the OS keyring: the macOS Keychain, or a Secret Service keyring on Linux and WSL2.
- Mount `~/.majhi` read-write.
- **Runs and previews reach only their own task.** Every runner container starts through `majhi-netguard`, and every preview runs inside the network of a small holder container that runs the same guard (the preview is the task's own image, whose entrypoint majhi cannot change). The guard runs as root with `NET_ADMIN` and sets iptables rules, then drops to the owner's uid with an empty capability set and no new privileges. It fails closed: no rule, no run. Private destinations are denied by default. Open: loopback, replies to connections that came in (the owner's browser to a preview), the whole public internet over IPv4 and IPv6, the task's own network (majhi passes its subnet; a network made after the run started is added at once with a `docker exec` of the same script, and removed when the network goes), majhi-server on its one port (runners only, the port the guarded `/mcp` path uses) and the DNS servers the runtime gave. Refused: the addresses the host's names resolve to and every gateway (the computer itself and its `127.0.0.1` services, majhi's API included), `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `169.254.0.0/16`, `172.16.0.0/12` and `192.168.0.0/16`, and for IPv6 `fc00::/7`, `fe80::/10`, mapped IPv4 and the host's IPv6 addresses. That covers another task's network, services and previews, the peer runners on the shared runner network (OrbStack routes between networks), the computer's LAN address and a private cluster or machine behind a VPN. **Consequence: agents cannot reach anything on a private range.** The way to a service on the computer or the LAN is a `host` connection (5.14). Every container a task starts is third-party code too, so none has a guard of its own: each runs in the network namespace of a holder that runs this guard (the same pair as a preview, see Containers for agents), and holds no `NET_ADMIN` to change the rules. That is the one rule for services, a script's `docker run`, compose services and the agent's own container: the public internet and the task's own network, nothing private. The task network itself stays `--internal` (it has no gateway, so no route leaves it); the only route out is the holder's interface on the runner network, filtered by the guard. Public IPv6 stays open so dual-stack and IPv6-only servers work.
- The host's keyring (the macOS Keychain or a Secret Service keyring) is not reachable from the containers. Login credentials live in each account's folder under `~/.majhi/accounts/<id>/`, and only the sign-in file is shared with the agent homes. Tracker tokens and API keys live in `secrets.age`, decrypted at startup with a key passed as a Docker secret.
- Provide a `MAJHI_RUNNER=native` option that spawns agents directly on the host instead of in the runner container, for when bind-mount performance hurts (large test suites on macOS). UI and services stay in Docker either way.
- Ship `docker-compose.yml`, a `.env.example`, and a `Makefile` or `justfile` with `up`, `down`, `logs`, `login <account>`, `doctor`.
- Healthchecks on every service. `doctor` checks: SSH agent reachable, each workspace root mounted, each account's auth, CLIs present with versions, git identity per org, disk space for worktrees.

## 5. Key mechanisms

### 5.1 Agent runtime (ACP)

- majhi spawns one ACP agent process per run with an explicit environment built from scratch: PATH, HOME, TMPDIR, locale, the agent's config home variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`), the account's API key variable if it is an API-key account (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`), git identity for the org. There is no SSH agent socket: agents cannot fetch or push over SSH, and only majhi's own git uses the forwarded agent (4.5). Never pass majhi's own environment through.
- Tools live in a registry (`packages/acp/tools/`). Each entry declares: the ACP launch command, the config home variable, the API key variable, how login works, and how to detect limit errors. v1 ships Claude Code and Codex. Adding Cursor, OpenCode or another agent from the ACP Registry means adding one entry with its tests.
- **Models and effort levels are never hardcoded.** majhi reads them from the agent's ACP session config options (categories `model` and `thought_level`, plus `model_config`), caches them per account, and refreshes them when a session starts. If an agent's saved model or effort is no longer offered, majhi warns in Studio and the room and uses the agent's own default until the owner picks again.
- Working directory: the task folder `<tasks_dir>/<task-id>/`, so the agent sees every repo in the task.
- majhi is the ACP client: it creates sessions, sends prompts, streams updates to the room, and answers permission requests according to the agent's permissions (auto-allow what is permitted, ask the owner otherwise).
- Model and effort per run, highest priority first: the owner's override for this task, then the agent's fixed `model` and `effort`, then, for `auto`, the role's model and effort tiers (Hub setup, overridable per org and agent), moved at most one step by how much work the decision provider (5.12) rates the task, resolved against the newest models the account offers (or the agent's `models` list). When the rating does not count (the gate below), the role's tiers apply unchanged. majhi applies the choice with `session/set_config_option`. The chosen model and effort, and why, are posted as a room event and recorded on the run.
- Attach MCP servers per agent from its `tools` list: `serena`, `majhi-memory`, `majhi-room`, `majhi-tasks`, `majhi-projects`, `majhi-connections`, `majhi-decide` (off unless the agent lists it, 5.12), `majhi-processes` (on for every agent, 5.15), plus any others the owner adds.

### 5.2 Accounts, per-agent homes and skills

- A login account has one config home holding its credentials. Login runs the tool's own login inside the runner, shown in an embedded terminal (device-code or browser flow). An API-key account needs no login: its key is stored in `secrets.age` and injected only into runs on that account.
- Several agents can share an account but need different skills. Agents of one workspace on one account share that workspace's agent home (see DECISIONS 2026-10-21; the 2026-09-29 reasoning against a linked credential file still holds, which is why the sign-in file is bind-mounted, not linked), so per-agent skills reach a run through the run itself, never through a shared `.claude/skills`.
- **Skills** use the open Agent Skills format: a folder with a `SKILL.md` whose YAML frontmatter has `name` and `description`.
  - **Store.** Installed once into `~/.majhi/skills/<name>/`, with `skills-lock.json` beside them recording source, ref or commit, content hash and install time.
  - **Install.** The Vercel `skills` CLI, pinned in the runner image, runs non-interactively in a runner with a throwaway home: `skills add <source> -y --copy --agent claude-code codex [--skill <name>]`, telemetry off. Sources: `owner/repo`, repo or `tree/.../skills/<name>` URLs, other git URLs, a SKILL.md or archive URL, a folder inside a workspace root or the tasks folder, or an uploaded zip (extracted with path containment). Private repos use the org's git login. Installing is two steps: a preview (name, description, files, source) and a confirm of exactly what was previewed. Installing never enables.
  - **Per agent.** One place decides who has a skill: the rules in `skills-lock.json` (all agents, one workspace, or one agent's own opt-in or opt-out; the agent's own choice wins). Agent files hold no skills list. The Skills page and the Agent page edit the same rules. Each run gets read-only copies of only its agent's enabled skills in a folder of its own, removed when the session ends, and the session's first prompt names each skill with its SKILL.md path. Changing an agent's skills restarts its open sessions when their turn ends, so the next turn has them.
  - **Browse** searches the skills.sh directory and shows each result's source repo. Update previews the change first; remove drops the skill and every rule about it. Every install, update, enable, disable and remove gets an audit row.
- **MCP servers** are `mcp` connections (5.14), installed from the same page: the official MCP Registry (`/v0.1/servers`, falling back to `/v0`), a remote URL (Streamable HTTP or SSE, with headers), a local command, or a pasted `mcpServers` snippet. A registry package is always pinned to a version. Fields marked secret are set through the write-only secret flow, required ones must be filled before saving, and Test runs right after and shows the tool list. Per agent, a workspace server is turned on in the agent's `connections`, inside its own org only. Global servers are included automatically.
- **By message.** In a room, the owner's "@agent install this skill <link>" or "@agent add this MCP server <name or link>" gets one approval card (what, source, which agent). Approving installs it and turns it on for that agent; secrets an MCP server needs are asked for with secret requests, never in chat. The same `skills.*` and `mcp.*` commands serve the page, the room and the captain.

### 5.3 Rooms and coordination

- Every agent turn's final message is posted to the room. **Nothing an agent writes wakes another agent.** An @mention between agents does nothing and the `mention` tool is gone; agents join a task only by the owner's @mention (an agent not in the team joins if its `where` allows this org, or it is a root agent; otherwise majhi asks the owner) or by a plan step that names them.
- **Lead and workers is the only team.** A task has one agent unless the owner picks a team on it (or the captain proposes one and the owner confirms): a lead and at most 3 workers. The lead writes a short plan with `record_plan`: at most 8 steps, in order, each naming the agent that owns it (`me` is the lead). The plan is stored in `task_plans`, and each step carries its own progress there (`todo`, `doing`, `done`, `stopped`, its one result line, how many times it was sent back). Steps are not tasks.
- **Workers get work only from the plan.** majhi hands the first step to its owner with a handoff prompt (the step, the plan with where each step stands, the diff stat). When that agent ends its turn the step is done: one result line goes in the room ("Step 2 of 4 done by @name: ...", what the agent reported with `step_done`, else the first line of its message) and the next step starts. One step runs at a time, so two agents never edit the same worktree at the same time (majhi still holds a lock per worktree). An agent that waits on the owner (an ask card, a question) keeps its step until it ends a turn without one.
- **Review before the owner.** A workspace setting, `rooms.review_before_owner` (on for every workspace but Private, off for Private; the owner changes it per workspace): when on, majhi ends the plan with a review step by an agent on a cheaper model (the agent's account's cheapest model by the price ranking, set as that agent's model for the task). A plan with no other agent to review gets none. The reviewer calls `send_back` with a step number and why: that step and the ones after it run again. A step sent back a second time stops, the task pauses, and Needs you shows the reason.
- **Staffing.** The lead's team facts (in TASK.md and at each wake) list for every agent: model, price tier, what is left of its account's windows (headroom), what it cost this task so far, and whether this computer is busy. TASK.md tells the lead to do small or short-budget steps itself and to add a worker only when the plan is worth it.
- Owner messages go to the mentioned agent, or to the team's lead if nobody is mentioned.
- Agents can also post through the `majhi-room` MCP tool (`post`, `read_recent`, `record_plan`, `step_done`, `send_back`).
- Parallel builders on different repos of the same task are allowed, by the plan: one step at a time.
- A task kept from before: the pipeline and the build and review loop are gone; a task that used them reads and runs as lead and workers (migration 192). The loop guard (`rooms.max_agent_turns`) and `rooms.review_rounds` are removed from the settings; an old file that still has them loads and the keys are ignored.

### 5.4 Tasks, briefs, branches, attachments

- Parsing rules from 3.1 run on the server too (shared code in `packages/shared`).
- Defaults: base branch from the org, working branch `{type}/{slug}` from the task's short name (a project's `branchPattern` wins). If the owner names an existing branch, check it out in the worktree instead of creating one.
- Create one worktree per repo with `git worktree add`. Fetch first. Fail loudly on conflicts or a dirty base.
- Generate `TASK.md` at the task root: brief, repos with branches and paths, team with roles, attachment list with summaries, recalled memory, org rules (commit identity). Keep it short. Regenerate when the team or repos change.
- Attachments: images are passed to agents that support images, and noted in TASK.md. Documents are converted to text once and summarized once, and the summary goes in TASK.md with the full file available on disk. Links are fetched once, stored as markdown in `attachments/`, and summarized the same way.

### 5.4a Parent tasks, child tasks and dependencies

- **One link model.** A task has links of three types: `parent` (it is part of a bigger task), `depends-on` (it waits for another task), and `follow-up` (created from another task, like the fix tasks of an ops task, 5.15). Links are stored in `majhi.db` and shown on both tasks.
- **Parent and child tasks.**
  - A task can have one parent. Nesting can go several levels deep.
  - Each child is a full task: its own room, team, repos, worktrees and branch.
  - The parent shows its children's progress ("3 of 5 done") and a rollup of their statuses. It moves to `done` when every child is done, unless the owner closes it earlier.
  - Children already made keep working. Nothing makes new ones from a split: `tasks.split` writes steps into the task's plan (5.3).
  - The task list nests children under their parent, collapsed by default.
- **Dependencies.**
  - `depends-on` points at one or more tasks. Cycles are refused when the link is made.
  - A task with an unmet dependency does not start. When the last one is met, majhi starts it automatically, subject to the concurrency limits (5.17).
  - Each link says when the dependency counts as met:
    - `merged` (default): the dependency's MRs are merged. The waiting task starts from the updated base branch.
    - `ready`: the dependency reached `review`. The waiting task stacks its branch on the dependency's working branch, and is rebased when that branch changes.
  - If a dependency is closed without finishing, the waiting task pauses with reason `owner` and asks what to do.
- **Context for agents.** `TASK.md` lists related tasks in one or two lines each: the parent and its goal, what this task waits on or builds on (with the branch), and its children. Agents do not read other tasks' rooms unless they ask for them.
- **Commands.** `tasks.link`, `tasks.unlink` and `tasks.split` are commands like any other (5.16), so the UI, the palette, the captain and agents use the same rules.

### 5.5 Multi-repo MRs and merging

- On approval, push each repo's branch through its SSH alias and open one MR per repo.
- Each MR description lists the task, the brief summary, and links to the sibling MRs.
- Merge order comes from project links (a repo that others depend on merges first), overridable by the owner.
- Who merges is the workspace's Merge row and its ship rules (5.18), not a switch of the org. The owner may always merge a task's open merge requests with one click, or merge on the host and click "I merged it". The captain merges them in order only where the ship decision for that task says Captain, Autonomous is On, and CI passes (no CI result for two minutes after the push counts as green). A protected repo is never merged by majhi. `orgs.<id>.merge` of older config is moved into the Merge row on start (`auto-if-green` becomes Captain) and removed.
- After merge: remove worktrees, update the tracker if linked, run the Housekeeper.

### 5.6 Memory

Two layers:

1. **Repo memory:** `AGENTS.md` in each repo. Human-readable, versioned with the code. Only curated facts get promoted there, by owner approval.
2. **majhi memory:** a local fact store in `~/.majhi/memory/memory.db`.
   - SQLite with FTS5 for keyword search and `sqlite-vec` for vector search. Embeddings run locally with a small open embedding model (for example through transformers.js). No external API calls.
   - Each fact: text, scope (global, org, or project), source task, source agent, status (pending, active, retired), pinned, promoted, use count, created and valid-from/valid-to timestamps (so facts can be retired when they stop being true).
   - Exposed to agents as the `majhi-memory` MCP server: `recall(query, scope)`, `propose(text, scope)`, `list_recent(scope)`. Agents can only **propose**. Only the owner or the Housekeeper, with owner approval, makes a fact active.
   - At task start, majhi recalls the top facts for the task's org and repos (hybrid search, capped at about 500 tokens) and puts them in TASK.md.
   - After a task, the Housekeeper reads the room and proposes new facts, duplicates to merge, and facts to retire. They show in the task's Memory tab and in Studio under Needs review.
- Why not Mem0 or Graphiti: they call a model through an API key to extract facts. Most of the owner's accounts are CLI subscriptions, and the store should work offline and cost nothing either way. Here the thinking happens inside an agent running over ACP, and the store never calls a model.

### 5.7 Resilience: checkpoints, limits, offline

- **Checkpoint** after every agent turn: record the ACP session id, the room position, and a WIP commit on the task branch in each touched worktree (`wip(<task-id>): checkpoint N`). On final approval, majhi squashes or rewrites WIP commits per org preference.
- **Resume:** use ACP session loading if the agent supports it. Otherwise start a new session with a handoff prompt built from TASK.md, the room summary and the diff since the last checkpoint.
- **Usage limit:** detect limit errors from each tool (collect the exact error shapes per tool and auth type in its registry entry, with tests). For API-key accounts, rate-limit and quota errors count as limits. Mark the account at limit, with the reset time if the error gives one. Then, under the org's auto-handoff switch:
  - a **worker** that cannot run (limit, signed out, an error, safeguards with no other model) has its step moved to the best other agent that can run (a worker or the lead: most headroom, then least spent), from the last checkpoint with a handoff note that carries the plan and the diff; the room says so in one line
  - a **lead** that cannot run is replaced by the worker with the most headroom, who keeps the plan and its progress and is the lead from then on (the old lead stays as a worker); one room line says so
  - a one-agent task, or a team with nobody else who can run, uses the agent's fallback whose account is not limited
  - when nobody can run, the task pauses at the checkpoint with one hold, `agents-down`, whose card names every account and its fix (sign in, or the reset time), shows in Needs you, and lifts by itself when any account is back (an account change event, and the limit sweep). The step then goes to the best agent that can run; the cut run is closed so the step never runs twice
  - otherwise pause with reason `limit`, and auto-resume at the reset time if enabled
- **Priority preemption.** `tasks.start` with `priority: urgent`, or `tasks.update` making a waiting task urgent, with every running place taken, pauses the lowest-priority running task at a checkpoint with hold `preempted` and one room line ("Paused for project · Name (urgent). Resumes when a slot frees."). It stays in the line (priority, then age) and starts again by itself when a place frees. The owner may pause any running task; the captain only tasks it or an agent made, unless the call carries `ownerAsked` from the owner's chat turn. `now` is not a preemption: it still goes past the cap.
- **Offline:** detect network failure (failed agent requests plus a periodic connectivity probe). Pause all running tasks with reason `offline`. When the connection returns, resume them from checkpoints, or wait for the owner if auto-resume is off.
- **Sleep and wake:** the host helper notices a wake (a jump in wall-clock time, or macOS power events) and tells the server. Turns that failed or stalled while asleep resume on their own from the last checkpoint.
- **Shutdown and reboot:** at login the host helper makes sure Docker and majhi are running. Tasks that were running when majhi stopped reload and resume on their own.
- **Crash:** if majhi restarts, tasks that were running resume on their own from their checkpoints. If a resume fails twice, the task pauses with reason `error` and the room says why.
- **What resume means.** Files the agent changed are already on disk in the worktree, and each turn ends with a checkpoint, so no finished work is lost. A reply that was streaming is cut off, and a command that was running (for example tests) is killed; the agent is told to continue and runs it again. Auto-resume is on by default and can be turned off per org.

### 5.8 Health, usage and status

- Agent status: working (on which task), paused, at limit, idle, error.
- Account health: auth valid, current-window usage, weekly usage, reset time, re-login warning. For API-key accounts: tokens and cost per day and week, and rate-limit errors.
- Where each CLI exposes usage or auth status through a command or ACP, use it. Where it does not, estimate from majhi's own token counts per account and label the number as estimated in the UI. Record per CLI in `docs/DECISIONS.md` what is measured and what is estimated.
- Health check button per agent: verify the CLI starts, auth is valid, and the model is available. If a real call is needed, use the cheapest model and rate-limit checks to once an hour per account.

### 5.9 Token optimization

Build these in, and record their effect in token receipts:

1. Handoff prompts instead of full chat history (5.3).
2. A short TASK.md brief with capped memory recall (5.4, 5.6).
3. Documents and links summarized once, full text only on demand (5.4).
4. Skills load only name and description until an agent uses one (Agent Skills behavior).
5. MCP tools gated per role: attach only the tools in the agent's `tools` list.
6. Serena for symbol-level reads and edits instead of whole files.
7. Stable prompt prefixes (system prompt, instructions, TASK.md header) so provider caching works.
8. Cheap models for routing, summaries and housekeeping by default, and the decision provider (5.12) for small typed decisions that would otherwise cost an LLM call.
9. A context budget per agent session with compaction at 80% (5.13), so no session grows until the window is full.

Token receipt per task: brief size at start, recalled memory size, total input, cache hit rate if reported, output, and per-agent split.

After a move, majhi runs `git worktree repair` and updates `majhi.yaml` in the same step.

### 5.12 Decision provider

Decision models answer typed questions against a state in one pass, with probabilities and a confidence score. They do not write text and do not speak ACP, so they are not agents. majhi uses them for small, frequent decisions.

- One interface, `DecisionProvider`, with four implementations:
  - **laya:** the default. Laya open-weights model (`convaiinnovations/laya`, 421M parameters, about 850 MB). Local, free, nothing leaves the machine. On Apple silicon Macs it runs natively through the host helper with `laya-mlx`, on the GPU. On Linux, Windows and Intel Macs, or when the native one is not available, it runs in the `laya` Docker service with `laya` on PyTorch, on the CPU or with CUDA on an NVIDIA GPU. `make up` gives it the GPU when Docker can use one (the NVIDIA Container Toolkit's runtime on Linux, the Windows NVIDIA driver on WSL2) and sets `MAJHI_LAYA_GPU=nvidia`: the image then takes PyTorch's CUDA 13.0 wheels (`MAJHI_LAYA_TORCH_INDEX` picks another index, such as CUDA 12.6 for a GPU older than Turing or a driver older than 580), and the generated override reserves the GPUs for `laya` and sets `LAYA_DEVICE=cuda`. `make up LAYA_GPU=off` keeps it on the CPU. Both load on first use and unload when idle. Weak without fine-tuning, reads about 512 tokens per state (English checkpoint), and gets worse past about 20 options, so questions must stay small.
  - **jev:** TypeSafe Jev hosted API. Needs an API key in `secrets.age`. Sends the state off the machine, so it is off by default and the owner enables it explicitly.
  - **acp:** simulates Jev or Laya with an ACP agent, for when neither is available. majhi sends the same state and typed questions as a prompt to a chosen agent (default: the Dispatcher, on its cheapest model and lowest effort) and asks for JSON only. The answer is checked with the same zod schema as the other providers, and retried once if it does not match. Its probabilities are self-reported, not calibrated, so the UI labels them as estimated.
  - **rules:** plain code, no model (the task box parser, fixed defaults). Always available as the last fallback.
- The owner picks the provider and a fallback chain in `majhi.yaml` (default: laya, then acp, then rules).
- Uses:
  - **Model and effort picking:** for agents with `model: auto` or `effort: auto`, pick from the options the account offers over ACP, given the task brief, repos and the agent's role (see 5.1).
  - **Routing:** which org, repos and team a new task or tracker item belongs to (Dispatcher); whether an agent message needs the owner.
  - **Memory:** is a proposed fact a duplicate, and which scope fits it.
  - **Safety:** flag text from attachments, links or tracker items that looks like instructions to the agent. This is a warning on top of wrapping that text as data (section 6), never a replacement for it.
  - **Any agent, as a tool.** An agent gets the `majhi-decide` MCP tool only when its `tools` list names it (off by default: no agent called it in five days, and its schema costs context in every session): `decide(state, questions)`, where each question is `choice` (pick from options), `score` (rate on a rubric) or `noul` (is this statement true). It returns typed answers, probabilities, confidence, and which provider answered. Agents use it for quick judgment calls instead of spending reasoning tokens: classify an alert, triage a log line, pick which service to check first, decide whether a finding needs the owner. Limits:
    - The state is trimmed to the provider's window (about 512 tokens for Laya's English checkpoint) and the answer says when it was trimmed.
    - At most 20 options per question.
    - A per-run rate limit catches loops.
    - Jev is only used when the task's org allows hosted decisions. Otherwise the call goes to the next provider in the chain.
  - **The owner, from the palette.** "Ask the decision model" runs the same tool on any text.
- Every decision records the full request, every answer's probabilities, the provider, the gate result and the outcome on the task. The decision provider is asked about the task, never about models, with described options, an abstain option and several option orders averaged. An answer counts only when it clearly beats chance and the runner-up (lift and margin, configurable in Hub setup); otherwise majhi falls back to rules or the role's tiers. The owner can mark a wrong pick, which builds the labeled set for tuning.
- Token receipts show which decisions replaced LLM calls, so the savings can be measured.
- **Fail fast.** Each provider gets a time budget (Laya 3 s, Jev 5 s, the stand-in agent 30 s) and the whole chain 30 s. A provider that is over budget is skipped at once, not cancelled, so a Laya that was loading the model is warm for the next call. After 3 failures in a row a provider is skipped for 60 s. The rules close every chain: their answer never counts, so the caller applies its own safe default (the role's tiers, wake the agent, ask the owner) with no slow call in between.
- **Cache.** Laya is deterministic, so an identical request is answered from an in-memory cache (3 days, keyed on the question kinds, options and their order, the normalized state, the provider order, the checkpoint and the calibration version). Identical requests at the same moment share one call. A hit reuses the first decision's id and writes no new log row. `decisions.status` shows the hit rate. Answers are cached before the gate, so a changed bar applies to a repeat.
- **Slots and labels.** A slot is one question of one use (`task-size`, `mention-wake`, `memory-verdict`, `tracker-project`, and so on) and is defined as data: id, use, question pattern, target precision and optional built-in fixtures. Adding a use is adding a slot. Labels (`decision_labels`) record the right answer to one question of one decision, with a source: `outcome` (free: a finished task's diff, turns and tokens bucketed into trivial to large; whether a woken agent acted; the owner's keep or drop of a fact; the project the owner picked for a tracker item), `owner` ("Wrong?" on a room line or a captain log line that reports a decision; the owner's label wins over an outcome) or `teacher`.
- **Eval.** `decisions.eval {use}` (owner only; a slot id or `all`) and the "Run decision evals" button in Hub setup run a slot on its labeled set and on its built-in fixtures through the real provider call and gate, and store the report: accuracy against the majority baseline, per-class recall and precision, precision and coverage at the gate, calibration error, whether a choice survives its options being reversed, p50 and p90 latency, and cost per 1,000 decisions. Two runs of the same slot at once share one run. Fixtures report only; they never make a slot live.
- **Calibration, shadow and live.** With at least 50 labels, an eval splits them by a fixed hash: 40% fit a temperature on the model's probabilities, 30% choose the lowest confidence bar that reaches the slot's target precision (at least 10 answers clear it), and 30% are held out to check it (target reached with at least 5 answers). Pass: the slot is **live**, and an answer counts when its calibrated confidence reaches the bar, it is not the abstain option, and every option order names it. Otherwise, and for every slot with no calibration, the slot is in **shadow**: Laya's answer is logged with its probabilities and compared with the outcome, never counts, and the caller falls back. So task size and model pick keep the role's tiers until a slot passes. A new checkpoint puts a live slot back in shadow until it is evaluated again. Uses an agent or the owner reads themselves (`tool`, `owner`) keep the lift and margin bar. A slot whose definition says `startMode: live` (the effort-delegation check, which was verified by hand and whose shadow would let a delegating effort through) acts on the base bar until it has a calibration.

- **More work for Laya** (captain v2, step 12; `apps/server/src/decisions/uses`). The owner asked that Laya take the cheap, frequent calls, as slots with a rules fallback each. The order for any call is rules, then Laya, then the smallest model, then the big model, then the owner; a call that names `order: ["laya"]` never falls through to a paid model, and one that names a stand-in carries `perDay`, a cap counted in the decision log so a restart does not reset it. Every use asks through one helper (`askOpinion`): one call, a hard time limit (4 s, 2.5 s for the wake gate), an answer that is not one of the options or not a probability is dropped, the rules' guess is dropped, and an answer acts only when its slot is live, majhi's gate accepted it with every option order agreeing, and its calibrated confidence is at least 0.9 (exactly 0.9 acts). Shadow slots log what they would have done and act on nothing. Six uses:
  1. **Own work second opinion** (`own-work-second`, shadow at start, target 0.99). The rule table keeps every refusal. Laya is asked only about the unknown middle: a plain lowercase program the table has no row for, every argument a plain name inside the worktree, no secret name, no network word, no chaining or redirect, no publish, deploy, delete, reset or install word, at most 300 characters, not an interpreter, shell or fetcher, and not text that talks to the reader. It may answer "routine" or "owner". The module reads the table again itself, so nothing passed in is trusted; a yes still needs a prompt the permission rules call unsettled, an Allow once option, a task the captain started and the chore's recheck. Low confidence, down, slow, garbage or shadow: the owner, as before. The owner's own Allow or Reject of a prompt Laya was asked about labels the decision (`routine` or `owner`).
  2. **Finding triage** (`finding-triage`, shadow, target 0.95). For each new finding Laya says keep or dismiss and, for a dismissal, which kind of noise (a hit in a test or sample file, an advisory in a dev-only path, an item irrelevant to the project). The suggestion is stored on the finding (`findings.triage`, migration 141), shown in the Findings sheet ("Laya suggests dismissing: ...", with Dismiss as suggested) and in the captain's digest line. It dismisses by itself only when the slot is live, Laya is 0.9 sure, the severity is info or low, the source is one a sensor files (security, dependency, radar, ci, ui, log, setup, analysis, other) and the text did not try to instruct an agent; the reason starts "Triage by Laya" and the outcome scorecard counts it for nothing, like a fold. The owner can bring it back (Bring back). Rules give a plain suggestion (all evidence in test or sample paths, every advisory dev-only) when Laya is down, never a dismissal. The owner's dismiss, task or reopen of a triaged finding labels the decision `keep` or `dismiss`.
  3. **Memory escalation.** Where Laya is unsure about a waiting memory's verdict, its relation to the nearest fact or a suspected secret, the stand-in agent (`decisions.acp_agent`, else the captain; set it to the cheapest model) answers the same question once, at most 40 a day, and its answer counts when it clears the review's own bar. A judgment call ("ask") and a contradiction stay the owner's by design. The stand-in's answer is also a teacher label on Laya's decision. Down, over budget or unsure again: the memory waits, as today.
  4. **Injection classifier** (`text-injection`, live at start on the base bar, because a flag only adds care; target 0.95). Rules (phrases only an attack has) always run; Laya adds a flag and never removes one. Used on a finding's text (triage), release notes before the radar's model reads them (they reach it inside the warning fence), and business memory content in a draft's context (`draftContextChecked`). A flagged text is wrapped in a warning fence (`<flagged-text>`, its own markers broken inside), shown to the owner as a small flag on the finding, and never used to pick anything: triage, the wake gate and Own work skip a flagged text.
  5. **Wake gate** (`wake-gate`, shadow, target 0.97). A soft wake over changed facts asks Laya, from the diff of the digest's facts, whether anything is worth a turn. A change to cards, waiting, holds, accounts, instructions, findings, the workspace or the Start row always earns a turn without asking. Low confidence, no answer or shadow: the turn is taken. One skip in ten is taken anyway, so the slot keeps seeing the outcome of what it would skip. After a turn the digest's facts are compared: unchanged means the turn was not needed, which labels the decision `skip`, else `turn`. In the simulated hour of 50 soft wakes over changed facts (8 real), turns went from 50 to 13.
  6. **Weekly eval** (the Upkeep playbook "Laya check", rules kind, once a week for the business from Private, no tokens). It runs the harness on every slot's stored labels and built-in examples, which refits each threshold on the labels it has (a slot that no longer reaches its target goes back to shadow), compares with the best earlier run on the same set (five points on labels, ten on the few built-in examples, at least 10 answered items, a run where Laya did not answer says nothing) and files a finding for each slot that got worse or is live under its target; the finding closes when it recovers. Hub, Setup, "What Laya decides" shows the run before and a red "Got worse" line per slot. It also reads up to 40 findings filed before triage existed.

### 5.13 Context budget and compaction

No agent session may keep growing until its window is full. Every session has a budget, and majhi compacts it before it gets expensive.

- **Signal.** majhi reads ACP `usage_update` (`used` and `size`) for every session. Both adapters send it today (`claude-agent-acp`, `codex-acp`). Gate on this provider-reported number, not on a byte estimate. If an agent sends no usage, estimate from majhi's own token counts and label the number as estimated.
- **Cap.** `context.cap` is the most tokens a session may use, whatever the model's window (default 200000; 0 is no cap). It merges majhi, org, agent like `compact_at`. `size` below is the cap when it is smaller than the window. Inside a turn the CLI enforces it where it can (see DECISIONS.md, PRV-47); majhi's own compaction runs between turns.
- **Threshold.** Compact when `used / size` reaches `compact_at` (default 0.8) of the cap. The default lives in `majhi.yaml`, orgs can override it, and agents can override their org. The check runs at the end of every turn and before sending any new prompt: if the last reading plus the size of the prompt about to be sent crosses the threshold, compact first.
- **How to compact, in order:**
  1. **Native compaction.** If the agent advertises a `compact` slash command over ACP (Claude Code and Codex both do today), majhi sends it with a short note on what to keep: the task, key decisions, remaining work, files touched, and the next step. The session stays the same, so the agent does not re-read anything. majhi then waits for the next `usage_update` and checks that usage fell below `compact_target` (default 0.4).
  2. **Handoff to a fresh session.** If native compaction is missing, fails, or leaves usage above the target, majhi asks the agent for a handoff note with a fixed template: original task, what is done, key decisions, remaining work, files touched, one concrete next step. The note is saved to `<task>/.handoffs/<agent>-<n>.md`. majhi closes the session and opens a new one with, in this order: the stable prefix (instructions, TASK.md header), TASK.md, the handoff note, a short room summary, the current diff stat, then the pending prompt verbatim. The agent is told to continue silently from where it left off.
  3. **Note built by majhi.** If the agent cannot write the note (the session is broken or already over the window), majhi builds it from durable state without calling a model: TASK.md, the last checkpoint, the room since that checkpoint (newest first, within a fixed budget), and the diff.
- **Rotation without pressure.** A session is also replaced by a fresh one (same handoff path) after `max_turns` turns (default 40, 0 turns it off), and whenever the owner clicks "Fresh session" on an agent in the room.
- **Turn limits.** One turn may run at most `turns.max_length` (default 2h), go at most `turns.idle` (default 25m) without output or tool activity, and optionally make at most `turns.max_tool_calls` tool calls (default 0, off). Orgs and agents override each field; `off` turns a duration off. A running `wait` process of the agent, or a permission prompt waiting for the owner, is not idleness, and no limit fires while such a prompt waits. A turn over a limit is cancelled, checkpointed and handed off (the agent writes the note within 5 minutes, except after an idle stop, when majhi builds it), and a fresh session continues with "Continue from the handoff note." The room shows one quiet line, like "@builder reached the 2 hour turn limit. Continued in a fresh session with a handoff note." When a task hits a limit 3 times in a row with no new commit in any of its worktrees, it pauses with reason `error` instead. The live agent row shows how long the current turn has run. Settings in Hub setup, Turns.
- **Reactive recovery.** A stop reason of `max_tokens` or `max_turn_requests`, or a context-window error from the agent, triggers the handoff path at once, using the note built by majhi. At most 2 compactions per turn (the cap is per turn, not per session). After that the run pauses with reason `error` and the room says why. The cap counts majhi's own compactions only, not the CLI's below.
- **The CLI's own compaction.** Inside a turn the CLI compacts on its own at the window majhi gave it at launch (Cap above). majhi did not ask, so it watches for it (PRV-103): first the adapter's report, a "Compact conversation" tool call that both adapters send to a client without ACP's compaction capability (Claude's carries the trigger and the tokens before and after; Codex's carries neither, so the size after is the next `usage_update`); else a sharp fall between two `usage_update`s of one session (under 60% of the reading before, and at least 20k tokens less) that majhi did not cause. Either one is recorded once, as method `auto`, with before and after when known, and posts the room's context line. Reports while majhi compacts itself, and Claude's `manual` ones, are majhi's or the owner's `/compact`, not counted again.
- **What is not carried over.** Old tool output and whole file contents. Agents re-read what they need, preferably through Serena at symbol level.
- **Budgets for what majhi adds.** Everything majhi puts into a context has a cap: handoff prompts, `majhi-room.read_recent` (last N messages, long ones trimmed in the middle with a marker), `majhi-memory.recall` (about 500 tokens), attachment summaries. Images count as a fixed token cost in estimates.
- **Visibility.** Each agent shows a context meter (used of size) on its avatar in the room and in the Context tab. Each compaction posts a room event, for example `@globex-builder compacted: 164k to 18k tokens (native)`, or `(auto)` for one the CLI did on its own, and is recorded on the run and in the token receipts of the task and the agent. majhi does not advertise ACP's compaction capability (unstable in ACP today): with it, claude-agent-acp keeps the token counts for JetBrains AIR only, while the tool call majhi gets without it carries them.
- **Tests.** A fake ACP agent that reports rising usage: compaction fires at the threshold, falls back to a handoff when `compact` is missing or does not reduce usage, respects the per-turn cap, and rotates after `max_turns`. The same fake compacts on its own inside a turn, with and without a report, and majhi records it once.

### 5.14 Connections

Connections give agents access to the systems the owner debugs and reports on: clusters, observability, mail, servers, cloud accounts.

- **Types** are registry entries, like tools, so new ones are cheap to add:
  - `kubectl`: a kubeconfig, one context, a default namespace.
  - `mcp`: any MCP server, local command or remote URL, with auth from `secrets.age`. For example New Relic's official remote server (`mcp.newrelic.com/mcp`).
  - `ssh`: a host alias from `~/.ssh/config`. Agent runs get no SSH agent socket (4.5); giving a run that holds an `ssh` connection its own access is decided when connections are built.
  - `env`: any number of named values for CLIs and APIs such as `aws`, `gcloud`, `psql`, OpenRouter or a video API. One connection can hold several, for example `API_KEY`, `USER_ID` and `ORG_ID` for one service.
  - `browser`: a browser the agent drives through a browser MCP server (Playwright or Chrome DevTools), with its own profile per connection, so each org's logins stay separate. Used for research and checking results; posting goes through platform APIs where they exist.
  - `mail`: an IMAP and SMTP account, or a mail MCP server.
  - `host`: a service on the owner's own computer (a local stack: ports 8000 and 5432, say), for one workspace. See "Services on this computer" below.
- **Fields.** Every connection type declares its fields, and each field has a kind:
  - `secret`: stored in `secrets.age`, entered once through a secure input, never shown again.
  - `text`: a plain value such as a user id, org id, region or endpoint URL. Stored in `majhi.yaml`, visible and editable.
  - `file`: a file such as a kubeconfig or a service-account JSON, stored in `~/.majhi/connections/<id>/`. The run gets its path in a named variable (for example `GOOGLE_APPLICATION_CREDENTIALS`).
  Each field maps to the variable name the tool expects. The `env` type lets the owner add any fields they need and pick the kind of each.
- **Storage.** Workspace definitions live under the org in `majhi.yaml`. Global definitions live in the top-level `connections` map. `global` is reserved for this scope and cannot be a workspace id. Only the owner creates or changes Global connections. Connection ids are unique across both scopes. Secret values live in `secrets.age`. Files such as kubeconfigs live in `~/.majhi/connections/<id>/` with owner-only permissions. Values are never logged and never written to TASK.md, the room, memory or reports. Agents see a connection's name and description, never its secrets.
- **Who can use what.** An org agent gets every connection of its org, plus every Global connection, while working in its own workspace. Root runs also get every Global connection. A connection's `agents_off` names the agents it never reaches; only the owner changes it, on the connection's page or the agent's page. A workspace may hold several connections of one service, each with its own name. A service whose MCP tools are split by product (DigitalOcean) is one connection with one sign-in and a `products` list; each product is its own MCP server on the run. A `git` connection gives runs glab (GITLAB_TOKEN, GITLAB_HOST) or gh (GH_TOKEN) with the workspace's own git sign-in, renewed by majhi; its reads run and its writes ask like any CLI. Global is an explicit owner choice; existing workspace connections are never promoted or shared automatically. Workspace environment values take precedence if a Global connection defines the same variable. Root agents can use every connection of every org. A run only gets what the task needs: the connections of the task's org, or for a root task, the ones the task names plus any the root agent attaches with `majhi-connections.attach`. Every attach is logged and shown in the room. An org agent never gets another org's connection.
- **How access reaches a run.** Built into the clean per-run environment (5.1): `KUBECONFIG` points to a per-run copy holding only that context; `env` values become variables; `mcp` connections are attached as MCP servers with their auth; `ssh` uses the forwarded agent socket. Everything is removed when the run ends.
- **Services on this computer (`host`).** Agents run in containers that cannot reach the computer they run on (4.5). A `host` connection is the one deliberate hole in that, per workspace and per port. Fields: a name, the host ports (1 to 65535, at most 16) and the workspace; never Global. Only the owner adds, changes or switches off one, on the Connections page: `connections.create` and `connections.update` refuse an agent or the captain for this type, an agent cannot attach one with `majhi-connections.attach` or name one when it creates a task, and majhi's own port (7070 and the port the server really listens on) is refused by the schema, the service and the forwarder's docker arguments. The one state is the usual one: saving opens a TCP connection to each declared port from where the forwarder runs, and the connection is `connected` only when every port answers, else `failed` (`unreachable` or `timeout`) with the port named; it is re-checked every four hours. Agents of the connection's workspace get it as every workspace connection (a root task only when it names it). Before such a run starts, majhi starts a forwarder container on the task's own network, named `<id>.host` there, that listens on the declared ports only, answers only peers of that network and passes each connection to the same port of the computer (`host.docker.internal`). Nothing else on the computer is reachable through it. TASK.md and `majhi-connections list` say `northwind.host: ports 8000, 5432`, and the room gets one line when the task has it. Removing the connection or changing its ports stops its forwarders at once. A connection that becomes connected (saved, or a check that passes) starts its forwarder at once in every task of its workspace that has a live session, posts one room line and tells each agent that `<id>.host` is now available with its next prompt; when it is removed or stops being connected the forwarders stop and the room gets a line. Agents can reach private ranges only this way (6).
- **Safety.**
  - The real guard is the credential. Read connections should use a read-only identity (a Kubernetes viewer role, a least-privilege New Relic user). Read-only flags in MCP servers are not enough on their own (for example containers/kubernetes-mcp-server issue #1415: its read-only mode could be bypassed).
  - On top of that, majhi's permission gate classifies commands and MCP tool calls that touch a connection. Reads (`kubectl get`, `describe`, `logs`, `top`, queries) run freely. Writes (`kubectl apply`, `delete`, `edit`, `scale`, `rollout restart`, `exec`, `drain`, sending mail) always ask the owner, unless the org's policy allows that exact action. A write that deletes or destroys something (delete, destroy, drop, purge, terminate, truncate, rm, wipe, prune, uninstall, a forced push, `reset --hard`, SQL `DROP`, `TRUNCATE` or `DELETE FROM`, a tool like `droplet-delete`) always waits for the owner's own click: no `allow` entry, "Allow for this task", approval rule or captain answer covers it, and its prompt says "This deletes or destroys something. Only you can approve it." Anything majhi cannot classify counts as a write.
  - Every write is recorded in the audit table.
  - Logs, alerts, emails and command output are data, not instructions (section 6).
- **Connect (remote MCP servers with OAuth).** The Connections page has a service catalog with a Global or named-workspace destination (`packages/shared/src/services.ts`: id, name, kind, MCP address, access in plain read and write sentences, test, docs, and whether the address was checked). Connect opens the service's own sign-in in the owner's browser through the host helper (or shows the link when the helper is offline) and waits ("Waiting for you in the browser", with Cancel). majhi finds the sign-in from the server's protected resource metadata, registers itself (dynamic client registration as a native client; a client metadata document when a public URL is configured), uses PKCE and the `resource` parameter, and takes the answer at its own `GET /oauth/callback`: `state` must be known, unused and under ten minutes old, `iss` is checked, and a denied or failed answer saves nothing. It then shows who signed in, the access in plain words, and runs the test, "Connected as X". Tokens live in `secrets.age` per connection and workspace, are renewed one request at a time with the new refresh token saved before the new access token is used, and never reach logs, the room or a run's environment. Runs get the access token as a header at session start; a session that holds a renewed connection restarts at its next turn end. States: connected, needs reconnect (the service refused the renewal), insufficient scope (offers "Allow more access", which asks again for the union of scopes), revoked, error. A reconnect as a different account changes nothing until the owner confirms. Disconnect revokes at the service where it supports that, deletes the tokens and removes the connection, and says what stays when it cannot revoke. Only the owner starts, answers or ends a connection.
- **Connect, step 2 (services without an MCP server, guided apps, command-line tools).** The same Connections page and engine (`state` single use, `iss` check, one renewal at a time, revoke on disconnect) also joins:
  - **Provider OAuth with PKCE S256 and the loopback redirect** for Outlook (Microsoft identity, public client), and Google's Gmail, Calendar and Drive. Each needs a client ID of an app the owner creates under their own account (`BUILT_IN_CONNECT_APPS` holds a public ID only if the project registers one, and never a secret). The grant is kept like an MCP one (`secrets.age`, per connection and workspace). A service with no MCP server becomes an `api` connection: a run gets a short-lived access token in one variable (`MICROSOFT_GRAPH_TOKEN`, ...), the refresh token never leaves majhi. X, LinkedIn, Linear's own OAuth and GitHub's device grant are not offered: X bills the app owner per call, LinkedIn gives no renewal, Linear has a better one-click MCP server and a pasted key, and GitHub's MCP server and `gh` need no app of the owner's.
  - **Guided app setup** for Google (one card for Gmail, Calendar and Drive on one Desktop client), Slack, Discord and the Microsoft client ID for Outlook. A sheet per app and workspace lists numbered steps with the exact console page to open, the exact values to paste (redirect `http://127.0.0.1:7070/oauth/callback`, `http://localhost:7070/oauth/callback` for Microsoft, the app name) and the permissions in plain words for the chosen access. Google: project, consent screen, permissions, a Desktop client; the owner drops the client JSON and majhi takes only a Desktop client whose addresses are Google's, stores it in `secrets.age` for that workspace and never shows it again. Then each service signs in on that one client, and two steps check themselves with the stored sign-in: each API answers (a 403 SERVICE_DISABLED names the exact page that turns it on) and the app is published (a token answer that says the refresh token ends in 7 days means the app is still in Testing, and the connection fails as `app-in-testing` with the publish page). Slack takes https redirects only, so the sheet generates the app manifest (Socket Mode, the pack's bot scopes) with a "Create from manifest" link and takes the bot token and app-level token in two secure inputs, checked against Slack before anything is saved. Discord takes the application ID and bot token (checked against Discord) and gives the add-the-bot link. The owner never edits a file or runs a command.
  - **Command-line tools per workspace**: vercel, stripe, aws, gcloud and az (GitHub and GitLab sign in through the git host sign-in, below). The host helper runs the tool's own login in `~/.majhi/connections/<id>/profile` (mode 700) with an environment built by the helper (its HOME and XDG folders inside the profile, the tool's own variables, a BROWSER that only prints the page; none of the helper's `AWS_*`, `GOOGLE_*`, `CLOUDFLARE_*`, `STRIPE_*` or `GH_TOKEN`), shows the device code or opens the page, and keeps the result only when the tool's check command works (and, on a reconnect, names the same account). The check command makes a real call and its exit code decides (0 passes, 127 is a missing tool, anything else is not signed in): a command that exits 0 when signed out, like `stripe config --list` or `wrangler whoami`, does not qualify, which is why wrangler and the Sentry CLI are not offered (Cloudflare and Sentry connect by one click or a token). Exit codes were run signed out: vercel 1, aws 253, doctl 1, gh 1 or 4. A failed, cancelled or timed-out login removes its folder and keeps the old sign-in. A `cli` connection mounts only that folder, read-write, into the runs of that workspace, with only the tool's variables pointing into it, never HOME. Disconnect runs the tool's logout and deletes the folder. Changes through the tool ask the owner like any connection write.
  - **Least privilege per pack.** Each scope has a plain sentence and a level. `read` is asked first; `readwrite` (drafts, calendar events) only when the owner turns on a pack that writes; `send` (Gmail send, Outlook send) only for a pack the owner lets send. Granular consent is checked: a permission the owner unticked shows as missing with "Allow more access". A sign-in with no renewal raises a reminder five days before it ends.
- **One state per connection.** A connection is `connecting`, `connected`, `failed` or `needs-attention`, and there is no separate "tested". `connected` carries `verifiedAt` and what the passing check did, and exists only after a real call with the stored credential passed: the service's API (who the token is, then one list), an MCP `initialize` and `tools/list`, or the tool's check command. `failed` is a connect whose check did not pass, with a typed reason and the exact fix (a page to open where there is one). `needs-attention` is a connection that worked and whose re-check now fails. The decision reads the call's result and never message text: an HTTP status, an MCP error code (an HTTP status the SDK puts in `code`, or a JSON-RPC code) or a command's exit code, mapped to a reason (`rejected` 401, `forbidden` 403, `insufficient-scope`, `not-found`, `rate-limited`, `service-down`, `unreachable`, `timeout`, `blocked-host`, `no-credential`, `expired`, `tool-missing`, `not-signed-in`, `helper-offline`, `setup-needed`, `app-in-testing`, `mcp-error`, `unexpected`). A check that fails without saying why is `unexpected`, never a pass. The state is saved (`connection_health`), a refused token renewal fails the connection at once, every connection is re-checked every four hours, and a connection that never had a state is checked once at startup. A connection that stops working for a reason only the owner can fix (not a network blip) becomes a finding. `doctor` runs them all.
- **Ways to connect, one entry per service.** The catalog groups by method: one click (remote MCP with OAuth and dynamic registration: the 13 first verified, plus Cloudflare's full server, Neon, PayPal, Intercom, Canva, Webflow and Zapier, each address probed on 2026-10-05; Asana is not offered because its authorization server publishes no registration endpoint), on this Mac (CLI sign-ins and `gh` or `glab` for git hosts), a pasted token (Bitbucket, Linear, Sentry, DigitalOcean) and your own app. A service that has several ways shows the best and keeps the others under "Other ways". "MCP server by address" probes the address with an unauthenticated `initialize`, reads the server's sign-in metadata, and connects by one click when the server lets majhi register itself, else takes a header token.
- **Git hosts.** GitHub (github.com and GitHub Enterprise), GitLab (gitlab.com and self-managed) and Bitbucket (Cloud and Server or Data Center) are connections. A sign-in to a host, by the host's own page or a pasted token, saves the token for the workspace as before and also makes a `git` connection (`provider`, `host`, how it signed in) with its own state, checked with two calls: who the token is, then one repository or project (GitHub Enterprise under `/api/v3`; Bitbucket Cloud with the Atlassian email and API token as Basic, Server with an HTTP access token as Bearer and `X-AUSERNAME`). A GitHub token page opens with a fine-grained token prefilled. A Bitbucket row says SSH may already work and the API token adds pull requests and the API. Removing the connection signs the workspace out of the host.
- **Self-hosted hosts and addresses.** A host the owner types (GitHub Enterprise, GitLab self-managed, Bitbucket Server, an MCP server by address) is refused when it is, or resolves to, this computer, a private network or a link-local address, unless the owner confirms that it is their own network; a cloud metadata address is never allowed. Number tricks (`2130706433`, `0x7f.1`) are read as the address they mean, a public name is looked up, a redirect is never followed with a token, and every call a server added by address leads to (its sign-in metadata, registration, token endpoint) goes through the same guard. Tokens are never sent through a third-party aggregator.

### 5.15 Task kinds, reports and live control

majhi replaces the agent CLIs for everything, not only repo work.

- **Task kinds.**
  - `code`: repos, worktrees, branches, MRs, as described above.
  - `ops`: no repo needed. Debugging, incidents, investigations, reports. It uses connections and can add repos later.
  - `chat`: one agent, no team, like opening a CLI. It can be turned into a `code` or `ops` task at any time.
  - The kind is inferred from the task box (Dispatcher and decision provider) and shown as a chip the owner can change.
- **Ops flow.** For example "why is the acme api down in prod": the agent (org or root) investigates with the org's connections and posts findings as it goes. It writes `REPORT.md` in the task folder: summary, timeline, evidence, cause, what was changed, and follow-ups. Follow-ups become either fix tasks, created through `majhi-tasks` and linked to the ops task, which go through the normal code flow with worktrees and approvals, or write actions such as a rollout restart, which wait for the owner's approval.
- **Seeing what agents do.** The room streams everything ACP reports: the agent's plan as a checklist at the top, each tool call (command, target, status, output collapsed), file diffs, and thinking if the agent shares it (collapsed). A one-line "now doing" status sits on each agent's avatar. Agents are told to say what they are about to do, in one line, before any step that changes something.
- **Stopping and steering.**
  - Esc stops the focused agent's current turn (ACP `session/cancel`). "Stop all" stops every agent in the task and pauses it with reason `owner`, keeping the checkpoint.
  - Typing while an agent works queues the message for its next turn. Cmd+Enter stops the current turn and sends the message at once.
  - Model and effort can be changed mid-session (5.1).
  - Permission prompts show inline with Allow once, Allow for this task, and Deny.
- **Media and pages from agents.** Agents show the owner things by saving them in the task folder and linking them in a message with markdown (`![chart](media/chart.png)`, `[report](media/report.html)`), or by sending ACP image content. The room renders images, video and audio inline, and shows pages, PDFs and other files as cards that open in a new browser tab. Web links are clickable. Task files are served only from inside the task folder, and HTML runs sandboxed in its own origin, so an agent's page cannot call majhi's API. The generated `AGENTS.md` tells agents how to do this.
- **Background processes.** Quick commands run in the agent's own shell. Anything slow or long-running (test suites, builds, dev servers, watchers) the agent starts through the `majhi-processes` MCP tool (`start`, `list`, `output`, `stop`, `restart`), so majhi owns the process. The ACP adapters majhi ships do not use client terminals, so majhi does not rely on them (DECISIONS.md, 2026-09-30). A process runs with the session's environment and mounts, in a folder inside the task folder. With `wait` (the default), when it exits by itself majhi wakes the agent that started it with the exit code and the last lines of output, and a task in review runs again; while it runs, the task stays running and the room shows "Waiting for" it. `wait: false` is for servers and watchers. Processes show in a Processes card in the task view: name, command, running time, port, output tail, and a Stop button or the exit code. Agents are told what is already running so they do not start a second copy. Stopping or closing the task stops its processes; at most 5 run at once per task.
- **CLI parity.** Slash commands the agent advertises over ACP work from the composer. `@file` mentions autocomplete from the task's worktrees. Pasted images and files attach. Any past session can be resumed. An embedded terminal opens in the task folder, and any file path opens in the owner's editor.

#### Containers for agents

Agents run without Docker on purpose (the socket is root on the host). When they need containers (to build and try a branch of majhi itself, or a database for tests), majhi runs them from a short list of actions, never a raw socket. The `majhi-containers` MCP tool (on for every session when majhi runs in Docker) has `preview_build`, `preview_run`, `preview_stop`, `service_start`, `service_stop`, `branch_db`, `list` and `logs`. The captain and the Hub have the same actions as `containers.*` commands.

- **The environment belongs to the project, not the task** (docs/briefs/workflow-reset.md, step 2). A task is a branch and a worktree. Its services, compose stacks and preview live in its project's environment (the project of its first repo, or the workspace's own environment when it has none). One task at a time holds a project's environment: the first call that needs it takes it, and the others wait in order, each with its place posted to its room ("Waiting for the acme-api environment, which PRV-3 uses now. PRV-7 is number 1 in line"). A waiting call gives up after `limits.env_wait` (default 30 minutes) with a clear answer; a task that goes back to running while another holds the environment takes its place in line and its services start again on its turn. The holder lets go when it leaves running (review, paused, stopped) or ends, after its containers are removed, and the next in line holds the environment at once (no polling). A service with no named volume keeps the environment while it keeps its data. A task that does not hold the environment sees none of its containers and can touch none, whatever name or id it types. Nothing is ever shared across workspaces: the builder, the package store, the network, the volumes and the images each belong to one workspace, and a volume that carries another project's labels is refused.
- **Names and labels, one place** (`apps/server/src/containers/names.ts`). Per workspace: the BuildKit builder `majhi-build-<org>` (and its guard `majhi-build-<org>-bg-<id>`). Per project: the network `majhi-<project>`, containers `majhi-<project>-c-<name>`, holders `majhi-<project>-h-<name>`, volumes `majhi-<project>-data-<name>`, the preview image `majhi-<project>-preview` and the images a script built `majhi-<project>-img-<name>`; a task with no project uses `<org>.ws` as its key. Every object majhi makes carries `majhi.container` (its kind), `majhi.org` and `majhi.project`; containers also carry `majhi.task` (the task that holds the environment now), and images the task that built them. Cleanup and disk hygiene select by these labels. A BuildKit builder cannot carry a label (`docker buildx create` has none), so a builder is found by its typed name, from the workspaces and task ids majhi knows.

- **Preview.** `preview_build` builds a repo's Dockerfile as the project's preview image `majhi-<project>-preview` on the workspace's BuildKit builder, as a process that wakes the agent when it ends. `preview_run` runs the image its own task built (another task's build is refused) with a throwaway folder (a named volume of the project, new for each run and removed when the preview ends) and nothing of the host, in the network of a guarded holder container (6) that is on the runner network (the route for its published port) and on the project's network as `preview`, with one port on `127.0.0.1` for the owner's link. The holding task's runners reach it at `http://preview:<port>`.
- **One network, one list.** Every container the holding task starts joins the project's network, behind the guard, and is reached by name from the agent's container and from each other: `service_start` services, a script's `docker run` through the shim, `docker compose` services, and (with a name on the network) a `majhi-processes` process. A container is a pair: the holder `majhi-<project>-h-<name>` (runner image, guard, `NET_ADMIN`, 64 MB, joins the runner network for the route out and the project network under `<name>`) and the container `majhi-<project>-c-<name>` in the holder's network namespace (all capabilities dropped but five, no `NET_ADMIN`). Both carry the labels above; the container is `majhi.container=taskrun`, the holder `taskhold`. The holder starts first and says when its guard is set, so a container never runs a moment unguarded. Egress follows the guard: the public internet works inside a service (`pip install`, `npm install`), private ranges, link-local, the computer, another project's network and the Docker socket do not. The `list` and `logs` tools and `docker ps`, `exec`, `logs`, `rm` cover every container of the task, whichever way it started. A holder is removed with its container, when the task ends or is removed, and at startup by label, so a crash leaves nothing.
- **Builds.** A build (a script's `docker build`, a compose `build:`, `preview_build`) runs on the workspace's builder `majhi-build-<org>`, shared by that workspace's tasks and never by another workspace's, so its cache serves every task and each layer is built once. The builder stops when the workspace's last build ends and holds no memory between builds. Its `RUN` steps run in the builder's network namespace, which a one-shot container closes with the same rules as a holder before every build (public internet only; it fails closed). Every image a Dockerfile pulls (`FROM`, `COPY --from`, `RUN --mount from=`, the `# syntax=` frontend) must be one the owner allowed or the task built; the rest asks the owner.
- **Names.** `preview`, `localhost`, the computer's names, `*.host` and `majhi-*` cannot be the name or alias of a container, a compose service or a process (`name_reserved`). A name a container of the task already has is refused (`name_in_use`).
- **Services.** `service_start` runs an allowed image (postgres, redis) as such a pair, with only named volumes majhi creates for the project. A port is never published. `branch_db` is for a task that changes the database schema: it runs `CREATE DATABASE <task> TEMPLATE <dev>` inside the task's running Postgres service (the dev database is the service's `POSTGRES_DB`, or `template`), so migrations never touch the dev data other tasks use. The copy is written down (`<majhi home>/cache/branch-dbs.json`) and dropped when the task closes, or, when its service is not running then, the next time that service starts.
- **Compose.** `docker compose up | down | ps | logs | exec` in a task reads the repo's own compose files (inside the task folder only; `compose.yaml`, `compose.override.yaml`, `-f`, `--env-file`, `--profile`) and runs each service as the same pair, in `depends_on` order (`service_healthy` and `service_completed_successfully` wait), with the same limits, labels, network and image approvals. The compose project is the environment's project (`-p` is ignored). `ports` are not published: a service is reached as `<service>:<container port>` from the task. `volumes` are folders of the task folder (never `.git`) or named volumes of the project; a task's `down -v` removes only the unnamed volumes of its own containers and leaves the project's declared volumes (`[volume_shared]` on stderr; deleting one is the owner's or the captain's command `containers.volumes.remove`); a volume with no source (an anonymous one) becomes a named volume of the project, `anon-<hash of container and path>`, with the same labels; `build` contexts and `env_file` stay inside the task folder; variables come from `.env` of the project directory only, never an environment. Anything that widens a container is refused before anything starts, with a code the script reads on stderr as `docker: [code] message` and in `error.code`: `compose_privileged` (also `cap_add`, `security_opt`, `pid`, `ipc`), `compose_host_network` (also `extra_hosts`, `dns`), `compose_device`, `compose_socket_mount`, `compose_mount_outside` (a bind or `driver_opts` outside the task folder), `compose_env_file_outside`, `compose_build_outside`, `compose_unsupported_key`, `compose_unsupported_flag`, `compose_invalid`. `docker run` takes `-p` (dropped, with a note), `--network name` (the project's one network), `-v /path` (a named volume, as above), `--env-file` (inside the task folder), `--user`, `--platform`, `--shm-size`, `--health-*` and `--network-alias`, and refuses the rest with the same kind of code (`privileged`, `host_network`, `namespace_not_allowed`, `device_not_allowed`, `socket_mount`, `mount_outside`, `limit_reached`, `image_not_allowed`).
- **Images.** A new image asks the owner once through an approval card (`containers.images.allow`) that names the image and the container or compose service that wants it, and PRV-49's always-allow rules apply. The answer allows the image in that task's workspace (`containers.org_images`, by workspace id, `private` for a task with none); the owner can also allow one everywhere (`containers.images`). `settings.get` lists both. The `majhi-containers` tools are trusted like the other majhi tools (no CLI prompt for each call); an image that is not allowed still asks.
- **Limits.** `containers` in `majhi.yaml`: `cpus`, `memory` (default 512m per service or preview), `per_task` (default 6 containers in a task: previews, services, a script's `docker run` containers and compose services, counted in every state until `docker rm`), `total` (default 8 across all tasks), `build_total` (default 1 concurrent preview build), `build_cpus`, `build_memory`. Starts reserve a global slot before allocating resources. A matching service start reuses the existing same-task service; a changed configuration requires stopping it first. The limits count the containers of the task that holds the environment.
- **Processes.** A `service_start` service and a preview are majhi processes: the Processes card, `majhi-processes output`, Stop and waking the agent work as for any process. A `majhi-processes` process runs in its own runner container; it joins the task's network under its name (`processHost`: the name lowercased), so the agent's shell and the task's containers reach what it serves at `<name>:<port>` when it listens on `0.0.0.0`. The `list` line shows that address.
- **Cleanup.** A task that leaves running (review, paused, stopped) stops its preview and services with saved volumes, removes the network, and hands the environment to the next task in line. A service without a named volume stays only while preserving unsaved data, with its network and the environment; it does not keep the rest of the stack running. An explicit Stop ends it. When none stay, majhi removes the network and keeps the volumes; when the task runs again they start again the same way. The workspace's builder stops when its last build ends. A closed task also removes the images it built and drops its copy of the database; the project's volumes stay with the project and go a week after its last open task closed, or at once when the project has no task left. At start majhi removes what the old model left for tasks that are not open: the task's own builder and its state volume, its preview image and its volumes (an object labelled with a task and no project); the builder of an open task only stops. Once a week it removes its own images that no container uses and builder cache older than 7 days (never volumes it did not label, never anything it did not label or name, never the build cache as a whole).

### 5.16 The captain and the control plane

The owner can run majhi by talking to one agent. The captain sets things up, changes them, runs tasks and debugs, the way the owner would use a CLI agent today, but with access to all of majhi.

- **One control plane.** Every change is a typed command with zod input and output, defined in `packages/shared/commands` and handled in majhi. Examples: create an org, clone a repo into a root and register it, add an account, start a login, create or remove an agent, set a limit, create a task, stop an agent. The UI, the palette, the captain and the tests all call the same commands. A feature is not done until its commands exist. There are no UI-only or file-only features.
- **Who the captain is.** `boss: <agent-id>` in `majhi.yaml`, by default a root agent on the owner's private account. The owner can make any root agent the captain, in Studio or by asking the current captain. The captain is always one keystroke away (Cmd J opens the Captain panel from any screen). The panel holds one thread per workspace and an "All" view (5.18); those threads are not tasks, never show in Chats or on the Board, and cannot be deleted ("Start fresh" clears one and keeps a summary). A topic chat the owner starts with the captain is an ordinary `chat` task. The captain has its own run slot, outside "agents at once" and "per account", so the owner's message is answered in seconds; its spend still counts against the autonomous budget and the account floors.
- **What it gets.** The `majhi-admin` MCP tool, which exposes every command, plus every other majhi tool and every connection of every org.
- **What it can do**, for example:
  - Clone a repo into a workspace root, create an org for it, register the project with aliases and links.
  - Create, edit, duplicate and remove agents. Assign them to teams and tasks. Change models, effort, context thresholds, limits and budgets.
  - Add accounts and run their login: it starts the device-code flow and shows the link and code in the chat, and the owner finishes in the browser.
  - Add and test connections.
  - Create, start, stop, reassign and close tasks. Interrupt or pause any agent.
  - Debug majhi itself: health, `doctor`, majhi's logs.
  - Install skills, curate memory, change the decision provider.
- **Approval policy.** Every command has a risk class:
  - `read`: runs.
  - `change` (reversible config, for example creating an agent or raising a limit): runs when the owner asked for it in the conversation. If the captain decides to do it on its own, it proposes and waits for a click.
  - `destructive` (remove an agent, org or project, delete a worktree, forget memory, move folders) and `outbound` (push, MR, merge, send mail, connection writes, sending data to a hosted service): always a confirm card in the chat, approved with one click.
  - The owner can change the policy per class or per command, also by asking the captain. Changing the policy is itself `destructive`. A destructive command always stays a confirm card: no mode or always-allow rule covers it.
- **History and undo.** `~/.majhi` is a git repository. Every command that changes a file commits it, recording who (owner, captain or which agent), which command, and why. Undo reverts that commit. Studio shows the history. Credentials, databases and caches are git-ignored.
- **Secrets never pass through a model.** When the owner pastes something that looks like a secret into any chat, the composer offers "Save as secret" and the agent only receives a reference such as `secret:newrelic-globex`. When the captain needs a secret, it asks for it through a secure input card that the UI renders, never as chat text.
- **Live changes.** Config changes apply without a restart (file watchers and in-memory registries). The only exception is adding or removing a workspace root, because Docker mounts are fixed at start. The captain says so and shows the command.

### 5.18 Autonomous mode and the captain's authority

The captain works like a chief of staff: the owner gives it a budget and authority per workspace, sees only the decisions that need them, and keeps one switch. The proposal and its reasons are in `docs/briefs/captain-chief-of-staff.md` (approved 2026-10-04).

**One switch: Autonomous, with an end time** (`docs/briefs/captain.md`, owner 2026-10-19 and 2026-10-20), in the console's top bar. One status line under it: "Autonomous · 2 working · $3.10 of $15 today · until 8:00". Its menu turns it on until the owner turns it off, until 8:00, until tonight (23:00) or for 2 hours, changes the end of a switch that is on, turns it off, and holds Pause all (stop the captain's work and its tasks at a checkpoint; a second press resumes).

- **On:** the captain takes tasks from the backlog and finishes them, in each workspace whose authority level lets it start work. A workspace at Ask me is never worked.
- **Off:** it works only when asked. Reading and answering never depend on the switch (only Pause all holds them). Turning off lets the tasks it started finish their current step, then they pause at a checkpoint; turning on resumes them.
- **The end time** (`autonomy_state.until`) is checked by the minute sweep; at the time majhi turns it off by itself and says why.
- **Fixed rules, not settings.** It never works on an idea (an agent's, its own, or one the owner kept): only tasks the owner made or approved, so a task the captain files without the owner asking is an idea. It works on at most `limits.captain_tasks` (default 2) tasks at once across all workspaces, and the owner's tasks go first in line: it takes a free place, never a place in the line. Each task's budget comes from its size (`limits.captain_task_cost`: small, medium, large); a task that spends it stops. A task that fails twice stops. Both stops are the owner's to lift (hold `autonomous-stop`); resuming gives it a new allowance. The day's cap (`autonomy.day`) and the account floors stay in Settings and hold every start.
- **The captain resumes what it or the switch paused**, and a task that stopped on a limit, a sign-in or an offline agent once that cause is gone; never one Autonomous stopped or the owner paused.
- **No stale beliefs about accounts.** The digest shows every account's state now. A queue item that waits for an account carries `waitFor`; majhi reads the account each minute and wakes the captain with one line when it holds.
- A task the captain or this switch paused says so: "Paused by Captain", "Paused when Autonomous was turned off", "Autonomous stopped it", never "stopped by you".

**One captain, one conversation, one account.** The console's Captain chat is the only conversation. With a workspace picked in the top bar the captain works scoped to it (that workspace's step); with All it reads across workspaces in the owner's own conversation and acts in one workspace at a time through `captain.step`. A step is a turn in that workspace's lane with only its own git, SSH, connections, wiki and account, and nothing of one workspace is carried into a step, brief, note, memory or message for another (checked in code: `captain/step.ts`). Lines of a step show in the conversation tagged with their workspace; the old per-workspace chat history stays where it was and is searched there. The captain's account (its agent file) runs every step; a workspace may name its own ("Captain uses this workspace's account"); the captain agent's `fallback` takes over at a limit; a workspace that cannot run is one Needs you row with its reason. The captain is offered the tools of its place (needs, work or chat) and starts every turn with the owner's standing intent, the workspace's authority level and the wiki overview.

**The Captain page** (Settings, `/captain`) shows History (what the captain did), Results and Findings. Each workspace's captain rules (Fix and Client update, the account, the daily budget, freeze dates, where it ships, AI providers, what it asks before sending) are on the workspace's page.

**Permissions by risk and one authority level per workspace** (`docs/briefs/workflow-reset.md`, step 1b; replaces the authority table, Own work, ship rules and full access). Every action an agent or the captain can take has a risk kind, classified from typed data in `packages/shared` (a command's name, the ACP tool kind and parsed words of a permission request, the docker shim's parsed argv, the image reference), never by matching text: `sandbox` (inside the task's worktree, containers and network: reads, edits, commands, installs, tests, builds, majhi's read tools, Docker Official Images and images the workspace allowed), `push-branch` (the task's own branch, a draft pull request), `merge-main`, `deploy-staging`, `deploy-production`, `client-message`, `client-server-write`, `delete-outside`, `secret` and `over-budget`. Each workspace has one level, set by the owner alone (Settings, workspace page: Ask me, Routine, Full; the command `authority.set` is no tool of the captain or any agent and refuses an agent's actor):

| Level | Goes ahead without a card |
|---|---|
| Ask me | `sandbox` |
| Routine (default) | `sandbox`, `push-branch` |
| Full | also `merge-main`, `deploy-staging` |

`deploy-production` and `client-message` ask at every level unless the workspace's incident settings say Captain ships (`fix`) or Captain sends (`clientUpdate`), which cover an incident's own fix and its client update; step 4 builds that flow. `client-server-write`, `delete-outside`, `secret` and `over-budget` always ask. A kind majhi does not classify (`other`) follows the approval modes of 5.16. Sandbox actions never create a card; they are logged, one audit row per kind of action per task per minute, for Done today. "Always" on a card saves one rule for the workspace and the kind of action (`push-branch`, `merge-main`, `deploy-staging`), never per task, agent or command line; for an image it is the workspace's image list. This level is the org policy that push, merge and outbound messages require. The rows the captain's code reads (start work, answer questions, answer approvals, upkeep, merge, push, deploy, tell) are derived from the level (`authorityFromLevel`) and not stored. A permission prompt is never the captain's to answer: a card exists because the level does not cover the action.


**Budgets.** An autonomous budget per day for all autonomous work (the captain's own turns and every task it starts or resumes), required while Autonomous is On. An optional workspace budget per day inside it; empty means the workspace shares the whole autonomous budget. Account floors and weekly budgets stay, on the same Limits screen under "Safety". When a budget runs out the captain asks as a decision ("Hooli used its $20 for today. 3 tasks are waiting. Raise it to $40 for today?"), and a held task names the budget that holds it ("Waiting for Hooli's daily budget, $20 used").

The **Limits screen** (`/limits`) is the one place for them: the autonomous budget per day with today's spend and a bar; one row per workspace with its optional daily budget (empty shares the autonomous budget), today's spend and a bar (the top bar shows today's spend under the Autonomous switch and a workspace's page takes its daily budget); and a folded **Safety** section with the account floors (what to keep of each 5-hour window and week) and the weekly budgets per workspace and account, which also limit the owner's own tasks. Save and Cancel show only while a field changed. The sidebar switch's "Edit budgets", the Captain page, Hub setup and the palette lead to it. The autonomous budget is never empty: `autonomy.configure` changes it and never clears it.

**Budget decisions.** When the autonomous budget or a workspace budget is used up and a task waits for it, the owner is asked once per budget and day, in the bell (with Raise and Leave buttons), in Needs you on the Captain page and on the Limits screen. While the autonomous budget holds everything, only it is asked about. "Raise" doubles the budget for that day only: it is a dated override that never changes the saved budget and ends at midnight; the hold lifts at once and the tasks it held continue. "Leave it" keeps the budget; the question is not asked again that day. The questions are `captain.asks` (`budgets`) and `captain.answerBudget`.

**Review now.** The Memory page header runs the memory or cleanup chore of a workspace at once (`captain.runChore`, owner only), also while Autonomous is Off. One run at a time per chore and workspace; a run past today's cap is allowed once because the owner asked, and says so. Memories the old rule handed to the owner (before 2026-10-04) are reviewed once more (migration 124).

**Decisions.** Everything that waits for the owner is a decision in one inbox, with the captain's recommendation and one-click answers. The bell opens it. Alerts go out only for decisions.

- **One model.** A decision has a kind (question, approval, ship, budget, cap, paused, sign-in, secret), a workspace, a task when it has one, one plain line, its options (primary first), the captain's recommendation when there is one, when it arrived and a link that opens its context. Decisions are derived, never stored: from the pending cards of open tasks (ask, choice, owner question, permission, approval, secret request, review, paused), the captain's daily-cap and budget questions, and accounts that need a sign-in. An answered card, a raised budget or a signed-in account is simply gone from the list. `decisions.list` reads them; `decisions.answer { id, option, text? }` answers one through the path its card already has (answer, approve or reject, merge or mark done, resume, raise or leave) and returns what still waits. Only the owner answers: agents, the captain included, are refused. A question with several questions in one card, a secret request and a sign-in have no buttons; their link opens the place that answers them.
- **Recommendation.** The captain records its opinion with `majhi_decisions_recommend { id, option, reason }`, one option of the decision and one line, from its lane and for its own workspace, whether Autonomous is on or off. It is kept by decision id and shown as "Captain recommends **Rebuild**: keeps a backup branch, nothing pushed", with that option first and primary. Without one, an ask card's default shows as "The agent suggests ...", and a ready-to-ship card shows the captain's checks line as its recommendation to merge. The captain no longer writes "I would choose X" in chat for this.
- **The inbox.** The bell opens it as a popover with compact rows; `/decisions` is a triage screen, one screen with no tabs. Left, a queue with one two-line row per decision: the task's title (not "Ready to ship"), its kind, workspace and age, and the captain's pick as a chip ("Captain: Merge"); filters above it by workspace and by kind (Ship, Questions, Approvals, Budget, Paused, Sign-in) with counts. Right, the selected decision in full so it is decided without opening the task: what it is in a sentence, the captain's recommendation with its whole reason, for work to ship the agent's last message (about eight lines, "Show all"), the diff stat with the biggest files, what the captain checked and where each repo merges, for a question the full question and the agent's last message, and the actions pinned under it, main one first, with a reply box where the answer is words. Ship and budget come first, then the oldest. Answering selects the next decision. Keys: J and K or the arrows move, Enter takes the main action (the first one that is not blocked), 1 to 3 pick an answer, R opens the reply box, O opens the task, Esc closes the reply (and goes back below 1000px). Below 1000px the right pane is the page and the queue is its back view. A link from the bell or the Captain page opens `/decisions?id=`. Empty: "Nothing needs you." with when the last decision was answered here. A single answer has no Undo, because an owner's merge has no revert path and an agent reads a permission answer at once; a batch is held for 10 seconds so it can be taken back before it is sent.
- **Work to review.** A review card offers Merge (when the task has repos), Mark done and Ask for changes. Ask for changes sends the owner's words to the task's lead as an owner message and the task goes back to running (`decisions.answer` with option `changes` and `text`). A merge that does not finish (conflicts) is refused with the reason and the card stays. `decisions.detail { id }` reads what the right pane shows (hand-back, diff stat, checks, repos, full questions, and options that cannot be taken now with the reason, like Merge with nothing committed). Reasons the captain stored before the authority table are rewritten when a decision is built: a sentence about an old level ("is set to Keeps things tidy") becomes "In Acme you decide when work is merged."
- **Batch approve.** The queue has a checkbox per row. Click checks one, shift-click checks the range from the last one, `x` checks the selected decision and shift+`x` checks the range to it. With rows checked the strip under the queue offers "Approve N" and "Leave N" with one line of what each does ("Allow once 9, merge 2. 1 will wait for you."). With none checked and several like the selected one (same kind, same task), it offers "Approve all like this (N)". Approve takes the option a decision marks `effect: approve` (allow once, never a remembered allow; Merge only for work the captain checked; Resume; Raise) and Leave takes `effect: leave` (reject, keep the budget); a decision without that button, and one whose recommendation is another option (a request the captain recommends rejecting), is not taken and stays. Questions are approved only where the agent or the captain suggests an option. A secret, a sign-in and a question without a suggestion are never batched. The click is held for 10 seconds with Undo and "Do it now", then sent as one `decisions.answerBatch { batch, intent, ids }` (owner only; at most 1000 ids; a page that closes inside the 10 seconds sends it at once). Each decision is answered on its own and one after another: a failure or a gone decision does not stop the rest, and the result lists `done`, `skipped` (with the reason) and `failed` (with the error). The same `batch` key sent again returns the first result and does nothing. The queue draws only the rows on screen, so 500 decisions stay fast.
- **Alerts.** Desktop and browser alerts are sent only for decisions, once per decision, and a burst becomes one "4 decisions need you". A card the captain is about to answer by itself (Autonomous on and the row on "Captain decides") alerts only if it is still waiting after two minutes. What the captain tells without asking (a chore turned off) is read in its log and never alerts, except the one morning brief push; its daily-cap and budget questions are decisions and do.

**Workspaces never collide.** One session per workspace ("lane"), reading and acting in its own workspace only. While Autonomous is On the agent slots are split evenly across the workspaces with runnable work; a workspace with nothing to run leaves its share to the others, and the owner's own tasks come first. Workspaces that share an account take its per-account slots and floors in turn. The captain never runs two tasks that write to the same repo and base branch at once unless their plans touch different areas (the top-level folders of the files each changed or names; no information counts as overlapping), refusing with one line and keeping the task in the backlog ("Not starting ACM-14: ACM-12 is already changing acme-api on main. It waits."), and ships into one base branch one at a time, in order. The owner's own starts are never blocked.

**Staffing.** For each task the captain weighs the task's size and kind, every agent that may work in the workspace (role, skills, model, effort), each account's free slots and usage left, floors and budgets, expected cost, past results on similar work in the repo, and the repo rule, with no built-in preference. It picks the team that does the work best, from one agent to a lead with builders and a reviewer, and says why in one line, which is posted in the task room when the task starts ("Team: @acme-lead leads on claude-acme-2: free slot, 60% of its window left; @acme-builder joins to build."). It does this when it creates or starts a task without naming a team (`tasks.staff` shows the proposal without acting); a team it names is kept. Another workspace's agents and accounts are never considered.

**Lead handover.** The lead, the captain or the owner can make another team member the lead (`tasks.setLead`): when the lead's account is at its limit, the task needs another skill or model, or the lead is stuck. The new lead must be on the team or able to join it (same workspace, an account that can run); the old lead stays as a builder unless `keepOldLead` is false. Any other agent is refused. A handover note in the room carries the plan, what is done and what is next, and wakes the new lead; the lead's task brief says when to hand over.

**Labels.** Every captain action is labelled "Captain", never "You", in rooms, cards and the log, with its reason and Undo where Undo exists.

**The morning brief** (`docs/briefs/captain.md`, owner 2026-10-20) replaces the daily summary, the agenda brief and the Today page. One short brief per workspace and local day, made once at the brief hour (`brief_at` in the Autonomous settings, default 08:00 in the owner's zone, the wall-clock hour also on a day the clocks change), whatever the mode. A row per workspace and day in `workspace_briefs` is the once-per-day rule, so two tabs, the minute sweep and a restart share one brief. Code gathers each workspace's facts from that workspace's records only (tasks taken on, shipped, merged, failed, spend against its budget, findings new and fixed, what the captain decided and ran, what waits on the owner, what the captain plans). The smallest model (the Housekeeper's agent, cheapest model) words them in at most six lines, one call per workspace with only its own facts; with no model, a bad answer or a slow one (20 seconds) a template says the same facts. Free text from findings and tasks goes into the prompt as one short line inside a fenced data block that stored text cannot close, and a reply that is empty, too long, carries a link or drops the count of things that need the owner is not used. A workspace with nothing done and nothing waiting is stored, costs no model call and shows nowhere.

Where it shows: a Done item in Needs you ("Read it" opens the captain conversation scoped to that workspace, where the brief is also a line), and the bell. It pushes: one message a morning to the owner's alert channels (ntfy and Telegram, the desktop banner too), one combined short line across workspaces ("Acme: 2 shipped, 1 needs you; Globex: quiet"), built from counts only, never a title or a client's words. A row in `brief_pushes` makes it once a day. It is not an incident ping: it does not use `pingFor` or the incident ping record and never changes them. The owner's muted `brief` kind and quiet hours hold it back (it is sent when quiet hours end). A morning when nothing happened anywhere sends nothing.

**The weekly client report** (`docs/briefs/captain.md`). On Monday at the brief hour in the workspace's zone, for each workspace that has a linked client chat, the captain makes the report of the week before (Monday to Sunday), once per workspace and week (`weekly_reports`). Every figure is derived from records: tasks shipped, hours of agent work (the sum of run spans), the agent cost, incidents and uptime (minutes failing over the minutes of the week, by the same function as the incident report). A week with nothing in it makes nothing. No model words it: a template does, so the text is the facts and nothing else. There are two copies. The internal one says everything and lands as a line in the workspace's captain conversation. The client copy says counts only (never a task title) and shows the agent cost only when the workspace's "Show cost to client" switch is on (off by default). It goes only to the chats whose "Gets weekly report" switch is on (off by default); with none on, it stays internal. The workspace's Client update switch decides the rest: Ask me holds it as a "Weekly report for <chat>" row in Needs you (Send report, Discard; Edit is in the chat), Captain sends sends it and leaves a Done item "Client told: weekly report". Both go through the one client reply path, so the fixed rails (a secret, another client's or workspace's name, an internal id) hold it either way.

**Upkeep.** Short runs at fixed moments, never a captain that stays awake:

| Chore | When it runs | What the captain does |
|---|---|---|
| Ship finished work | A task reaches review and its checks pass | Merge and push "Captain decides": ships by the workspace's ship rule. "Ask me": asks. |
| Approval cards | A card arrives | Answers routine ones by the workspace's Approvals rules. Risky ones and the never list go to the owner. |
| Agents' questions | An agent asks | Never decided by Laya. A permission prompt is settled by a rule table (majhi's own read tools allowed; force pushes, recursive deletes, root, downloaded scripts, keys and similar rejected; a prompt with no readable text is the owner's), else by the captain's own turn, else the owner. A question is answered by the captain's turn from the brief, memory or code, or by the owner. An agent that asks the same thing again within 10 minutes, or a third question within 5 minutes, is left for the owner ("@agent keeps asking in TASK (4 times in 5 minutes); it may be stuck") and gets one message to stop asking. |
| Memory | Daily, and when 10 memories wait for review in a workspace (at most four runs a day), and when the owner presses Review now | Reviews waiting memories with a bar: a durable, non-obvious fact for later tasks is kept; a one-off symptom, generic advice, a restatement of how majhi works, a flaky or timing note, or what the repo docs already say is dropped; a copy is merged into the fact it repeats. Only a contradiction or a rule that would change how agents behave broadly waits for the owner. Each step names its reason in the log and can be undone. Private also reviews global memories; a client workspace never sees them. |
| Projects | A new repo appears, and daily | Registers it in the right workspace with base and remotes. Asks when unsure. Never touches protected repos. |
| Task triage | Daily | Sets priority and due dates, marks duplicates and stale tasks. Suggests closing; never closes. |
| Cleanup | Daily | Removes worktrees and containers of done tasks. Never removes uncommitted work. Also frees disk in done tasks, in code with no model: after `cleanup.free_after_hours` (default 24) it deletes what a task can rebuild (`node_modules`, `.pnpm-store`, `.turbo`, `.next`, `.vite`, `test-results`, `playwright-report`, `.venv`, and `dist`, `build`, `target` only when the repo ignores them), and after `cleanup.worktree_after_days` (default 7, 0 is off) a clean worktree whose commits are merged or pushed, through the worktree removal the cleanup already uses. It never deletes a tracked file, never follows a symlink, skips a task when any of its repos has a change to a tracked file, and rechecks that the task is still done before each folder. The log line says the bytes freed. It runs while Autonomous is Off, like the rest of Cleanup. |
| Stuck tasks | Nobody works and nothing is pending | Wakes the lead once, then tells the owner (5.3). |
| Follow-ups | Daily | Reads the open follow-ups of memory for the workspace. Closes one whose task is done or that a later task did, merges a repeat of an older one, and reports the rest as findings, proposing a task (inbox, not started) for concrete work. One captain turn at most, for follow-ups that may already be done. |

**One captain, one conversation per workspace.** There is only the owner's captain. It keeps a separate session per workspace ("lane"), so one client's code and details are never in its context while it decides for another. Lanes share only the owner's global instructions and counts, never content. The threads are not tasks: they appear only in the Captain panel (Cmd J and the Captain page), never in Chats, on the Board or in task search, and they cannot be closed or deleted. "Start fresh" ends a thread's session and starts a new one carrying a summary (the same handoff as "Fresh session" in a room); the messages stay. An old address of a thread (`/t/<id>`) opens the Captain page on that workspace's tab.

**Findings.** One deduplicated store for everything the captain's playbooks and the agents notice (captain v2, `docs/briefs/captain-v2-playbooks.md`).

- **A finding** has a workspace, an optional project, a source from a shared registry (follow-up, security, dependency, ci, log, ui, radar, opportunity, setup, incident, competitor, grant, launch, deal, social, inbox, analysis, legal, other), one title line, detail, evidence (links, file:line, commands run), a severity (info, low, medium, high), an optional goal and playbook id and an optional channel for outputs that would leave the machine, a dedupe key, and a status: open, proposed (became a task in the inbox that has not started), task, decision, dismissed (with a reason) or fixed.
- **Dedupe.** The same key in the same workspace is the same finding: reporting it again moves its last-seen time, adds evidence and only raises severity. Without a key it is the source, the project and the title. A fixed finding that is reported again opens again; a dismissed one stays dismissed.
- **Commands.** `findings.list` (read; filters by workspace, project, source, status), `findings.report`, `findings.update` (status, severity, title, detail), `findings.toTask` and `findings.dismiss` (reason). Agents get them as tools with no card: `majhi_findings_report`, `majhi_findings_update`, `majhi_findings_toTask`, `majhi_findings_dismiss`, `majhi_findings_list`.
- **Who may do what.** An agent reports into its own task's workspace and changes or dismisses only what it reported itself. A captain lane reads and changes its own workspace's findings only. The owner sees all. `findings.toTask` makes a task in the finding's workspace and links it: from the owner it is the owner's task in the inbox; from the captain it is a proposal, an inbox task that is not started (until the Own work row exists, every captain task from a finding is a proposal). The finding follows the task: started, it becomes a task; done, fixed; deleted, open again.
- **The follow-ups playbook** (the `followups` chore, daily) is the first one. By rules and embedding similarity, with no model turn when nothing is new and one batched turn when some follow-ups may already be done. Each action is a line in the log: "Closed follow-up: ... (fixed in PRV-105)", "Proposed task: ...".
- **Triage by Laya.** Each new finding is read by Laya before the captain hears of it: likely real or likely noise (a secret-scan hit in a test fixture or sample config, an advisory in a dev-only path, a radar item irrelevant to the project), stored as `triage` with the reason and the confidence. The suggestion shows in the sheet and the captain's digest. A finding is dismissed by the triage only when its slot is live and calibrated, Laya is 0.9 sure, the severity is info or low and the source is one a sensor files; the reason starts "Triage by Laya", the outcome scorecard counts it for nothing, and the owner can bring it back, which labels Laya wrong. A finding whose text tries to instruct an agent is flagged, never read by a model for a verdict and never dismissed, and goes into a task inside a warning fence. See 5.12.
- **On the Captain page** the Now column has a Findings section (the number seen in the last day, the top three open ones, the tasks they became, See all). The sheet filters by group (Open, Tasks, Dismissed, Fixed, All), workspace and source, renders only the rows on screen, and works by keyboard (arrows or j and k, Enter for the detail, t to make a task, d to dismiss with a reason).

**Playbooks, goals and the outbound gate** (captain v2, step 6). A playbook is the one unit of standing work, stored as data; one scheduler fires them.

- **A playbook** has an id, name, pack, one-line purpose, a trigger (a cadence with optional quiet hours, plus the events it listens for), a scope (each workspace it is on in, or the business), the inputs it may read, its steps as a short instruction, its outputs (finding, task, draft, decision, log), the outbound channels it may draft for, a cost tier (rules, Laya, small model, big model) with a token budget per run, and the goal it serves. The shipped ones are data in `apps/server/src/playbooks/builtin`; the owner turns each on or off per workspace and changes its cadence, quiet hours, goal and settings (`playbooks.update`, owner only: the captain never changes its own playbooks). Cadences: on demand, when something happens, every N minutes, daily at a time, weekly on a day. Daily and weekly times are the workspace's wall clock: an hour a clock change skips runs just after it, a repeated hour runs once, a run missed while majhi was off is one catch-up run, and a clock set back never fires a playbook twice.
- **Packs.** Upkeep: the nine chores of the table above, one playbook each, plus "Laya check" (rules kind, weekly, once for the business from Private, no model: it runs the decision evals, recalibrates and files a finding for a slot that got worse; see 5.12), carried out by the same chore under the same guards, caps and log (what they do and when they run did not change; a chore the owner turns off never starts, by schedule, event or Run now). Engineering: the five sensors of step 9 (below), on by default. Ops watch: the services the owner lists per workspace, and anything else worth watching (databases, Redis, servers, queues, prices and pages, metrics, a check in words; see Watch anything), checked as code with no model (addresses every 5 minutes, certificates and names daily, an optional read through a monitoring MCP connection), incidents with a timeline, escalation and a phone push (see Ops watch below).
- **The runner.** Per workspace, a playbook is held when Stop everything is on, when Autonomous is Off and it is scheduled upkeep (Ship, Cards, Questions, Memory and Cleanup react and still run, each by its row), when its Upkeep row is You, when the workspace rests (hours, freeze), when it is in quiet hours, or after failures. One run per playbook and workspace at a time. A failed run backs off 15 minutes, doubling to 6 hours, and the owner is told after the second failure; Run now ignores a backoff and quiet hours but nothing else. A rules playbook runs as code. A captain playbook first runs its preflight in code: with nothing new it wakes nobody and spends no tokens. Otherwise it wakes the workspace's lane with the steps, the budget and the run id, treats the owner's settings and everything it reads as data, and ends when the captain calls `majhi_playbooks_report` (done, nothing, blocked). Nothing new is archived quietly. A run that reaches its token budget is cancelled and capped, and one that never reports ends after 20 minutes as failed.
- **The page** `/playbooks`, under Captain in the sidebar and linked from the Captain page: a list by pack with a switch, the next run and what came of the runs on each row; the selected playbook in full (when, settings, goal, steps, budget, history); Goals under the list; a Sending sheet for the outbound gate. Findings carry the playbook that filed them, so each playbook shows its findings, how many were taken up and how many dismissed.
- **Goals** belong to a workspace or the business, with a title, an optional metric, target and due date, and a status. The owner's are active; the captain proposes one in its own workspace and the owner confirms it (`goals.*`). A playbook and a finding link to a goal.
- **The outbound gate.** Whatever would leave the machine (email, social post, comment on a public tracker, form submit, message) is offered through `outbound.submit` and nowhere else. Per workspace and channel the mode is Draft (the owner approves each; the default), Batch (queued, put in front of the owner at the channel's batch hour) or Auto (sends within 5 a day; selectable only through a promotion the owner accepted in Decisions after a track record, see Outcomes below; any other Auto row reads as Draft). A draft shows in Decisions with its text, target and voice; Approve sends it, Discard drops it. Text with a secret in it is refused. Text in a draft is data and never changes its path. Only the owner decides a draft. No sender is connected yet: an approved draft is marked approved with "no sender is connected for this channel yet" and nothing is sent, until a channel gets its transport with its connection (steps 11a and 11b).

**Outcomes, the scorecard, the trust ladder and one cost ceiling** (captain v2, step 8). `apps/server/src/outcomes`, migration 138, commands `scorecard.get`, `scorecard.setMinutes`, `trust.list`, `trust.unmute`, `trust.setWindow`, `money.get` and `money.set`.

- **Outcomes.** Every output of the captain gets a judgment later, kept in `outcomes`, one row per output, joined by value to its workspace, authority row or outbound channel, playbook and task (so it outlives a deleted task). The outputs: a line of the captain's log (a chore or playbook action, a ship, an approval, an Own work approval), a task the captain started, an outbound draft, a finding, and the owner's answer to a decision the captain recommended. The results: kept, undone, reverted, merged then reverted, task failed, accepted, dismissed, approved, rejected, overruled, edited (reserved: drafts cannot be edited yet), or gone (a started task deleted before it finished; it counts for nothing). They come from signals that already exist: Undo in the log (a ship that is undone is "merged, then reverted"), a task the captain started that paused after an error, in circles or blocked (failed) or finished (kept), the owner's "Wrong?" mark on Laya's decision behind an action (overruled), a finding dismissed or taken, a draft approved or discarded, and an answer that is not the captain's recommendation (overruled). A pass recomputes each judgment from what is there now, so an undo an hour or a week later changes the outcome it belongs to. An action nobody takes back counts as kept six hours after it. Passes run at boot, every five minutes and when the scorecard is read.
- **The scorecard.** Per workspace, per authority row and outbound channel, and per playbook, for today or this week (the owner's calendar, in their time zone): actions, kept percent, undone or overruled percent, tokens and dollars, owner minutes saved and findings that became fixes. Cost is the captain's lane turns plus the turns of the tasks it started; a row or playbook that only has tokens is priced at its lane's average dollars per token. Time saved is kept actions times the minutes of their kind (defaults: start 10, questions 3, approvals 1, upkeep 2, merge 5, push 3, own 1, draft 8, a finding taken up 15), which the owner edits (`scorecard.setMinutes`). With nothing done there is no percent, never a zero out of zero. The Captain page header shows one line per workspace for the week ("Acme Kept 47/50, $3.10, ~2.5 h saved", the three busiest and "+N more") and a Scorecard link that opens the full sheet (Today or This week, four tables and the minutes editor).
- **The trust ladder.** For each authority row and outbound channel of each workspace the ladder reads the last N judged outputs since the row last changed (N is 20, `trust.setWindow` changes it). Fewer than N say nothing. Under 80 percent kept (80 exactly stays) a row set to Captain drops to You, a channel on Batch or Auto drops to Draft, by itself, and one Decisions item (kind Trust) says so with the evidence: the outputs that were taken back. Its buttons are "Got it" and "Give it back". Above 95 percent kept over N, with nothing undone, rejected or overruled in 7 days, it proposes a promotion as a Decisions item ("Let it decide", or Draft to Batch to Auto for a channel), with "Not now" (the proposal does not come back for 14 days). A row set to You is judged on the captain's recommendations the owner followed. Nothing is ever promoted without the owner's click, and no Trust item can be approved in a batch. Accepting a promotion to Auto marks the channel's Auto as accepted and turns it on; `outbound.setMode` refuses Auto otherwise, even with `explicit`. A demotion takes that standing away.
- **Auto-mute.** A playbook whose findings were dismissed more than 70 percent of the last N judged ones (7 of 10 is not enough) and that is on and not weekly already is set to a weekly schedule (Mondays 08:00) and the owner is told in Decisions with "Undo" (it puts the old schedule back and starts the playbook's record again) and "Got it". The Scorecard sheet shows a muted playbook with an Undo link, and `trust.unmute` does the same.
- **One cost ceiling.** One monthly ceiling (`money.set`; the owner's, the captain cannot change it) across all spend: agent tokens, the captain's lanes and the playbook runs on them. The month is the owner's calendar month in their time zone. Laya runs locally and costs nothing; a cloud fallback of the decision provider is not priced per call yet and is not counted. `money.get` returns the spend, the ceiling, "at this pace $X by month end" (from the second day of the month) and the P&L. When the spend reaches the ceiling, new starts the captain makes are held: its wakes, chores and playbook runs rest, and a captain call that starts work is refused ("Not started: the monthly ceiling of $500 is reached"). A turn that is running is never stopped, and the owner's own starts are never blocked. The owner is asked once as a Money decision: "Raise to $X this month" (a quarter more, for this month only) or "Keep the ceiling" (the hold stays and nothing more is asked that month). A new month starts clean. The Captain header's spend line shows "$212 of $500 this month, on pace for $410" before today's spend. Health and usage has the Money panel: the ceiling field, a bar with the pace, and Profit and loss.
- **P&L per workspace.** Spend against value, from rates the owner enters per workspace: what the client pays per month (retainer) and the owner's hour. Value is the time saved at the hourly rate, and "retainer less spend" is the margin. A rate that is not entered shows "n/a" and nothing is invented: with none, a workspace shows its spend only.

**Sensors** (captain v2, step 9, `apps/server/src/sensors`). Cheap code, no model turn, that feeds findings with dedupe keys. Each is a rules playbook in the Engineering pack, marked read-only: it only files findings that wait, so it runs when Autonomous is off and when Upkeep is You (a resting workspace, quiet hours, a backoff and the schedule still hold). On by default; a workspace with no registered project has nothing to look at and the run says so.

- **Network.** Every sensor request goes through one guard (`Net`) with a fixed host list: `api.osv.dev`, `endoflife.date`, `api.github.com`, `registry.npmjs.org`, plus the git host of a project's own GitLab connection. Any other host is refused before anything is sent. Requests carry package names and versions, a product name, or a repo slug and branch; never code, a path, a project name or a secret. A 429 or 5xx retries twice (Retry-After honoured, at most 30 s), then the run fails and backs off as any playbook does; what the sensor knew stays and nothing is closed on a look that was cut short. What sensors remember is in `sensor_cache` (ETags, lockfile hashes, public answers, a token count).
- **CI health** (`eng-ci-health`, every 6 hours). For each project with a GitHub or GitLab remote and the workspace signed in to that host, it reads the pipeline runs of the default branch and of up to 5 open task branches with the workspace's own token. The branch head is read first with its ETag; a 304 on a green branch ends the look there, and a quiet branch waits longer (30 minutes, doubling to 12 hours, back to normal on a push, a running pipeline or a failure). A failing latest run is a finding of source `ci` per branch and workflow (default branch medium, high after 24 hours or 3 failures in a row; a task branch low, medium after the same); a pass after a failure on the same commit, or a second attempt that passed, is a flaky finding (low). A green run closes the finding; a task branch that is no longer open dismisses it.
- **Dependency sweep** (`eng-dependency-sweep`, daily). Reads the tracked lockfiles read-only (pnpm-lock.yaml, package-lock.json, yarn.lock, bun.lock, Cargo.lock, go.sum, poetry.lock, requirements*.txt, Gemfile.lock, composer.lock; at most 20 per project, 25 MB each; a malformed file answers nothing) and asks OSV in batches of 1000. The answer is cached by the lockfile's hash and asked again only when the lockfile changed or a day passed. One `security` finding per project that lists its vulnerable packages worst first (at most 20 lines: package and versions, fixed version, lockfile paths, severity, advisory ids; aliases such as a GHSA and its CVE are one), with the worst advisory's OSV summary as untrusted text cut to 200 characters; severity is the worst package's, low for a development-only dependency. Upgrading every package closes it. `dependency` findings for direct npm dependencies two or more majors behind the registry's latest (at most 10 per project, 40 registry lookups per run, cached 3 days).
- **Secret scan** (`eng-security-sweep`, daily). The tracked files (text, up to 200 KB each, no symlinks, not lockfiles or build output) through the same detector that keeps secrets out of memory. At most two `security` findings per project: high for values in a provider's own key format (private keys, AWS, GitHub, GitLab, Slack, Anthropic, OpenAI) and medium for values that only look like secrets (an assigned password, a long token, a JWT), each listing up to 20 `file:line` places; the value is never stored, logged or sent. Vendored and collected static files are skipped. It rescans when the checkout changed or after a week.
- **End-of-life watch** (`eng-eol-watch`, weekly). The runtimes with a version on the project card (Node, Python, Go, Ruby, PHP, PostgreSQL, MySQL, Redis, Java, Rails, Django, Laravel) against endoflife.date, cached a week. Past its date is high; within 30 days medium; within 90 days low.
- **Tech radar** (`eng-tech-radar`, weekly). For the ten npm dependencies a project imports most, the GitHub releases (the repo comes from the registry's metadata; conditional requests, 25 GitHub requests per run). A stable major or minor release newer than the installed version is put to the smallest model (the Housekeeper) with the notes in a fenced data block: does it matter to this project, and why in one line. The reply must be one small JSON object; the finding (`radar`, info, low for a breaking change, medium for a security fix) holds only that line, cleaned, never the notes. A budget of 30,000 tokens a week per workspace (estimated at four characters a token) stops the questions; releases not asked about wait for the next week. Nothing new means no model call.

**Ops watch** (captain v2, step 6a, `apps/server/src/ops`). The services the owner lists per workspace, watched by cheap code, with incidents, escalation and a phone push. The Ops watch playbook (`ops-uptime`, "Service watch") is its switch, cadence and history; it is read-only, and unlike the other playbooks it keeps looking while the workspace rests and through quiet hours.

- **Services.** Per workspace, on the Watch page (`/watch`, below Captain beside Playbooks; the row shows a lamp only while something is down). A service has a name, an http or https address (no sign-in inside it), an optional exact status (default: below 400), an optional keyword the page must contain, an optional latency limit, a certificate watch, a name (DNS) watch, an impact (High, Medium, Low) that sets the incident's severity, the project a fix opens in, and an optional monitor: one read tool of one of the workspace's remote MCP connections (Sentry, Better Stack, Grafana, Datadog) with its arguments, the path of one number in the answer and the limit above which it fails. Saving the first service turns the playbook on for the workspace. At most 50 per workspace. An older uptime check's `urls` setting is imported once as services.
- **Checks.** Addresses every 5 minutes (the playbook's cadence), certificates and names once a day (and on Check now). A failed address check gets a second look right away. The body of a page is read only as far as a keyword match (at most 256 KB, kept for nothing, the match is a boolean); status, latency and a fixed vocabulary of reasons ("status 503", "connection refused", "the expected text is missing", "slow: 4210 ms, limit 1500 ms") are all that reach a finding, a timeline, the captain or the screen. A certificate with 14 days or fewer left is a warning (incident capped at Medium), 3 days or fewer, expired or untrusted is a failure with the service's full impact. A monitoring connection that is not connected, not signed in or does not answer makes only that check "unknown": the address check keeps working. No network on this machine makes a failed look "unknown", never "down" (the network probe decides), and nothing is counted.
- **Flapping.** Counts live in `ops_state` (migration 139) and survive a restart: a window of the last 3 looks per check. An incident opens when 2 of the last 3 failed and the newest did (certificates and names after one more try). A service that fails again within 30 minutes of its incident closing reopens that incident (the count of flaps shows) with no new alert and no new wake, so a flapping service is one incident, one finding and one alert.
- **Incidents.** A confirmed failure opens an incident: a finding of source `incident` (deduplicated by service, severity by impact) and a row with its timeline (opened, alerted, escalated, acknowledged, what the captain did, reopened, resolved with the time open). The timeline is also the finding's detail. The workspace's lane gets a news wake with the evidence (data, not instructions) and what it may do within its authority rows: read logs and metrics through the workspace's MCP connections, read only; open a fix task in the service's project with `majhi_findings_toTask` (a code task, a proposal the Start row decides on); draft a status update with `majhi_outbound_submit` (the outbound gate, Draft); note what it learned with `majhi_findings_update`. It never restarts or deploys: restarts come later, only through runbooks the owner approved. The fix task and the draft are added to the timeline. Checks green for the resolve time (default 10 minutes) close it and fix the finding.
- **Escalation.** A high incident alerts the desktop at once (never held by quiet hours, mutes or a burst) and the phone. If nobody acknowledges it within the escalation time (default 10 minutes, set in Alerts) it alerts once more, louder, and says so in the timeline. Until acknowledged a high incident is a Decision (kind Incident, sorted first) with one button, Acknowledge; after the repeat its title says it was not acknowledged. Acknowledging stops the alerts and leaves Decisions; the incident closes when its checks are green. Acknowledge from Decisions, the Watch page or a phone link. A medium incident alerts the desktop once and respects quiet hours; a low one files a finding and wakes the captain. The desktop banner has no action button (the host helper's notice carries none): it opens Watch.
- **Phone push** (`ops/phone.ts`, off by default). Through ntfy, which needs no account: ntfy.sh or the owner's own server (with an optional token). One click in Alerts makes a topic of 144 random bits, stores it in secrets.age, returns it once with an `ntfy://` link shown as a QR code (drawn in the page; qrcode-generator, MIT, no network), and never returns it again (Set up again replaces it). A push is a title: the workspace's name and a fixed line ("a permission request waits for you", "incident, high"). No task title, code, URL, secret or client data. An unreachable ntfy never stops the desktop alert; majhi tries the push again every half minute while an incident waits. Decisions of the kinds the owner enables (permission requests, work ready to merge, drafts) are pushed once each, outside quiet hours.
- **Telegram ping** (`ops/telegram-owner.ts`, off by default). The same single incident ping goes to the owner's private chat with one of the workspace's Telegram bots. Alerts shows the exact message to send the bot (`/start` and a one-time code that works for 15 minutes); the chat is learned from that message and nothing else, and the paired chat is never stored as a client chat. One decision (`pingFor`, `packages/shared/src/incident.ts`) says whether any channel pings: when an incident opens, when it grows worse, and once more when a high one stays unacknowledged. Failing again inside the 30 minute window is the same incident and pings nobody.
- **Action buttons.** Acknowledge for incidents and Approve and Leave for the enabled kinds, only when the owner gave an address their phone reaches majhi on. majhi is not on the internet, so they work only on the same network (majhi has to listen on it) or through the opt-in tunnel; without an address a push only opens the ntfy app, and Alerts says so. A button is a link `/ops/phone/<ref>/<action>?t=<token>`: the reference is random and names no decision (the decision is kept in majhi's database, so ntfy.sh sees no task id), the token is HMAC-signed with a key from secrets.age over the reference, action, expiry and the decision, valid for an hour and spent by its first use. A replay, a changed byte, another reference or action, an old link, a kind the owner switched off, a decision that is gone, a new setup (new key) or too many wrong tries (20 in 10 minutes stops the route) get the same refusal sentence. Taking one button voids the decision's others. A GET shows a page with a button and spends nothing (link previews open links); the POST acts. Approve and Leave take the decision's own approve and leave options, and refuse when the captain recommends another.
- **majhi watches itself** (`ops/self.ts`). Every 5 minutes (the first look 90 seconds after start) Health's checks and some measurements of its own become incidents in Private: server stall (event loop), memory, free space under ~/.majhi and the backup folder, database size and growth, a stuck autonomous queue, the size of the task worktrees and e2e traces, and Laya when it errors. A failing check opens an incident after two failing reads in a row, carries the Fix button Health offers for it (a fix that needs a form or a sign-in sends the owner to Health), and closes when it has passed for the resolve time or is gone. Warnings are never incidents. Urgent ones (disk, host helper, backups, secrets key, runner, server stall, queue) are high and escalate like any other.
- **Commands** (`ops.*`, all the owner's; an agent is refused): `ops.overview`, `ops.serviceSave`, `ops.serviceRemove`, `ops.checkNow`, `ops.ack`, `ops.settings`, `ops.phoneSetup`, `ops.phoneSet`, `ops.phoneTest`, `ops.phoneForget`. The captain reads incidents as findings.
- **Watch anything** (`ops/anything`, `/watch`). The Watch page lists anything the owner wants to know about, as one list of rows (icon, name, workspace, live value, status) with filters by kind (with counts), status, workspace and a search. A watch has a name, a workspace, a kind, a check, an alert condition, how often (minutes to days) and what happens when it fires; its numbers are kept (`watch_samples`, migration 144: every look for 2 days, one an hour to 90 days) and its status is ok, alerting, changed, paused or unknown. Kinds, each a cheap code check with no model: website or API (status, keyword, latency, or a number at a JSON path); database (Postgres or MySQL: one read-only statement returning a number, through a Variables connection holding the database URL, run by a bundled Node driver in a read-only session; MongoDB: a JSON read command from an allow list (count, dbStats, collStats, serverStatus) with a path to the number; any other database through its official image's client in a throwaway container, with a read-only login; a cause on majhi's side is reported as "majhi problem: ..."; only a single SELECT, SHOW or EXPLAIN passes, never EXPLAIN ANALYZE, a locking read, a function that cancels, sleeps or reads files, or any write keyword, checked when the watch is saved, again at the port and in the session); Redis (memory against its limit, clients, keys or one INFO field, over a small RESP client that sends only INFO, DBSIZE and LLEN); server (an SSH connection: disk, load or memory with exactly `df -P <mount>`, `uptime` and `free -m`, nothing else is ever sent); queue (a Redis list's length or a count query); price or page (a public page fetched with no cookies, sign-in or owner headers, redirects followed by hand and every hop refused if it is on this machine's network; a value by CSS selector, text pattern or the page's own price markup, numbers parsed as prices, or a hash of the main text for a change); metric (one read tool of a monitoring MCP connection, a tool whose name starts like a write is refused); and custom in words (the captain looks on the schedule, at least every 15 minutes, with a stated budget of 3 tool calls and about 2,000 tokens, and reports a value or a state with `watch.report`). Alert conditions: above or below a number for N minutes, changed (an Acknowledge, "Got it", takes the new value as normal), contains or no longer contains text, down (two failing looks in a row). A secret from a connection is read from `secrets.age` only for one look and never stored or logged: an error from a database or host is replaced by a fixed phrase before anything is kept.
- **Automations are folded into Watch and Playbooks** (migration 145, `automation/migrate.ts`). There is no Automations page; `/automations` redirects to `/playbooks`. Watch gained two ways to look, with the same cheap code and no model: a file or folder in a project (the check `path`: the size and modification time of the file, or of every file in the folder, skipping `.git` and `node_modules`, `missing` when it is gone; only inside the project's checkout in the watch's workspace, a path that leaves it by `..` or a link is refused) and a URL (the price or page check in text mode, alerting on a change). "When it fires" gained an action majhi's own code runs, no model: start a task with a prompt (project, agent, title, text), post in a room, or run a process. It is the action runner schedules always used: everything it names must belong to the watch's workspace, text with a secret is refused, the overlap rule (skip while the last run goes) holds, and it is checked when the watch is saved and again at every run. `{{event}}` in a message or a task's text becomes a line about what fired; a command is never filled in. A watch with an action and its alert off raises no incident: each change runs the action once and the new value becomes the one to compare with. Its last runs show in the detail. Playbooks took over schedules: a clock playbook (runner `action`) is an owner-made playbook with an interval, cron or one-off time in a time zone, an action (the same three) and an overlap rule, run by majhi's own scheduler (no captain, no tokens), listed only in its workspace, on when made by hand and off when a sentence made it. The sentence planner may return one; the manual form is "Schedule an action". The migration copied every schedule into a clock playbook with its own id (so its run history shows on it unchanged), with the same time, zone, action, overlap, switch and next run, and every trigger on a file or a URL into a watch with its history. The other trigger kinds (task status, merge request, branch, process exit, usage, command output) became Watch kinds too and moved over the same way; the old trigger engine is gone and `triggers.*` remain as aliases. The `schedules.*` commands remain as aliases for clock playbooks.
- **Merge request reviews and limit watches in Watch** (migration 146). The MR poller (every minute, the existing cadence) now also reads review state from the host and keeps it on the MR record (`mr_review`, `RepoMr.review`: `approved`, `approvals`, `approvalsNeeded?`, `changesRequested`, `pending` reviewers). GitHub: the pull request's reviews through `gh api` (the latest approval or change request per reviewer; a comment does not count, a dismissal clears) and its requested reviewers and teams. GitLab: `glab api` merge request approvals (`approved`, `approvals_left`, `approved_by`) plus the merge request's reviewers who have not approved, and an unresolved blocking discussion counts as changes requested. Bitbucket: the pull request's participants (approved, `changes_requested`, reviewers who are silent), no extra request. The reads ask with `If-None-Match` and reuse the last answer on a 304 (GitHub and GitLab, and Bitbucket where it answers 304), kept in memory; a failed review read leaves state and CI as they were. The MR chip on the task's merge card shows one short line ("approved by 1", "changes requested", "1 of 2 approvals", "waiting on ana"). The Watch check `mr` gained `approved`, `changesRequested` and `reviewRequested` (one subject per asked reviewer, so a new request fires): like the other event kinds each fires once when a merge request joins the state. The Watch check `usage` gained percent sources beside spend: an account's 5-hour or weekly window (the cached account usage), a workspace's or an account's weekly budget (the budget monitor), the Autonomous daily budget and the monthly ceiling (money). Conditions: above N percent (once per crossing), `atLimit` (100 or more) and `resets` (fires once on the first look under the limit after one at it; it never fires for a window that was not at its limit). A watch may read an account of its own workspace or a private account, never another workspace's; a workspace budget is always the watch's own. A new "When it fires" action, `tasks.resume`, resumes the workspace's tasks paused by a limit that no budget or Autonomous hold still keeps. The planner reads "tell me when the MR for ACM-3 is approved", "tell me when claude-personal is at 90% of its weekly limit" and "when the 5h window resets, resume my paused tasks".
- **A sentence into a watch.** `watch.plan { text, org? }` asks the Housekeeper (the cheapest model, its own strict budget) for a watch as JSON, using the workspace's connections list; a reply that does not parse, names a connection that is not the workspace's or writes is dropped and rules read the common phrasings instead (Redis memory, a queue, database latency, row counts and replication lag, a server's disk, load or memory, a price under a number, a page that changes, an address that is down or slow), else the sentence becomes a custom watch. With no workspace given, the workspace whose connection the sentence names, else Private. It returns the watch, a one-line plan and a first test value; the page shows the plan with Start watching, Edit details and Cancel. `watch.test` runs a check once; Set up manually is the plain form.
- **When it fires** (per watch, editable on the page, defaults chosen by the planner): Alert me (a desktop alert, or a high incident with the phone when Phone alert is on; off files a quiet incident); the captain looks into it, read only through the workspace's connections, and writes what it found with `watch.report` (shown on the watch with an optional link such as the cheapest store); Fix it (Off, Ask me first, Do it then tell me) with a list of allowed fixes derived from the kind and the connection's access; draft a status note through the outbound gate; free text the captain follows ("Or do this"); when it recovers, tell me and close the incident with how long it lasted. Snooze (1 or 8 hours) and a maintenance window (2 hours) keep the watch looking but raise nothing. A price watch compares the stores the owner lists and never buys anything.
- **Fixes.** A fixed list, never one that drops, deletes or truncates data: kill queries running over N seconds (cancel, not terminate, from a fixed statement), restart a named service (`sudo -n systemctl restart <unit>`), clear `.log` files older than 7 days in a named folder under /var/log, all run by majhi's own code through the same ports and checked again there; and, done by the captain after the owner's yes through the connections it has, add an index (a task that ships by the Merge rule), roll back the last deploy, scale the database, scale workers by an owner's runbook. A fix that needs access the workspace lacks is listed with "needs X access" and a Connect link. With Ask me first, the question is a Needs you decision on the incident with buttons such as "Do both" and "Only kill queries", and nothing runs until the owner answers; only what is still allowed and possible runs. There is one attempt per incident, however often the incident flaps. After a fix the check runs again; not fixed in N minutes (default 15) or worse, majhi undoes what it can (the fixes above leave nothing to undo, and says so on the timeline), raises the incident to high and pages the owner, once.
- **Commands** (`watch.*`): `watch.overview`, `watch.plan`, `watch.test`, `watch.save`, `watch.remove`, `watch.checkNow`, `watch.pause`, `watch.snooze` are the owner's; `watch.report` is the one an agent may call. Incidents of watches are ordinary incidents (key `watch:<id>`) with the alerts, phone push and escalation above.
- **Not built yet:** restarts through approved runbooks, hypotheses with evidence on the incident page, a status page, the tunnel, an action button on the desktop banner, the ntfy doorbell for services that can only send webhooks.

**Wakes carry news.** A wake means something changed since the captain's last turn in that lane (captain v2, step 2).

- **News and soft wakes.** News: a task done, failed or ready for review, a new finding, a task new to the backlog, a card the captain may answer, a decision left for the owner, a lifted cap, an account that changed, the owner's message, Autonomous turned on. Soft wakes are alarms that mean something only if the facts changed: "running, but no agent is working", a restart, the hourly check.
- **A digest hash decides.** Just before a wake is sent, the facts it would show (holds, accounts, the workspace's tasks and their status, cards, the decisions left, the backlog the rules allow, the queue, project cards and open findings; not spend, usage windows, sizes or what an agent is doing right now) are hashed and compared with the facts at the end of the captain's last turn in the lane. Unchanged facts and no new news line: nothing is sent. A soft wake with no earlier turn to compare with is dropped. After a captain turn ends, the facts as they then stand become the baseline, so its own actions are not news to it.
- **Bursts are one wake.** Wakes within the debounce are one message with all their reasons, a repeated line counted ("x3"), and the newest ones shown.
- **Explained states never wake.** A running task nobody works on while it queues for a slot, waits for a process, waits on the owner's card, waits for an account, or is held by a cap or budget (the owner is asked about those already). A cap that starts wakes nobody; a cap that lifts does. The bare hourly check is dropped when the workspace has no backlog, no open finding and no decision waiting.
- **Start is You still gets thinking.** The captain has a lane in a workspace where Start is You when its Upkeep row is Captain. It is woken there for findings, follow-ups, tasks ready for review and project cards, and its rows limit what it does: it files proposals (`findings.toTask`, an inbox task for the owner to approve) and starts nothing. The digest says so.
- **Measured.** In a simulated busy hour (40 stall alarms, 12 real changes, 59 minute sweeps, one workspace), the old driver sent 49 wakes and the new one 12, one for each real change.
- **The wake gate.** A soft wake whose facts changed no longer always costs a turn: Laya reads the diff of the facts and says whether anything is worth one (5.12). A change to cards, the decisions left, holds, accounts, instructions or findings always does. Low confidence, shadow or no answer takes the turn. In a simulated hour of 50 such wakes, 8 of them real, turns fell from 50 to 13 and every real change still got one.

**`tasks.tell`.** The captain writes to the lead of a task in its own workspace, or to a named agent on its team, instead of editing a brief or restarting the task. The room shows a note "Captain to @lead: ..."; the agent gets the text like an owner message, marked as advice that grants no approval; a task in review goes back to running as it does for an owner message, and a paused, done or unstarted task is not written to. Agent tool `majhi_tasks_tell`, no approval card. Only the owner and the captain may call it. The captain in a workspace lane writes to that workspace's tasks only. The captain in its root chat (the All chip) writes to a task of any workspace, only when the owner asked for the note (`ownerAsked`). An ordinary agent is refused, the captain in any other chat is refused, and from a lane a task of another workspace is refused. At most 3 notes per task in 10 minutes (kept in memory; a restart gives a new window), so two agents cannot loop.

**Conflicts follow the Merge row.** Where Merge is Captain, the captain may call `tasks.resolveShip` (ask the lead to bring the target in, resolve the conflicts, run the checks and merge once). Where Merge is You it is a decision. The merge it ends in never pushes; pushing follows the Push row.

**Deploy.** A project lists where it is deployed in its config: environments in the order they go live, each with how (a GitHub workflow, a GitLab pipeline, a Vercel project, or a command over ssh that the owner wrote), how it is checked (a health address and or a watch, for a wait) and how it goes back. After a merge the ship rules decide each environment (Deploy staging, Deploy production; an environment named `production` is the second): the captain starts what they give it, the owner is asked on the task about the rest. A deploy ships only the head of the base branch when a task's merge produced it (or the owner confirms it), only after the environments before it are live at that commit, only through a connection of the project's own workspace, and once per environment and commit. It follows the run to its end, checks the target, and on a failed run or check rolls back at once, opens an `incident` task with the log (as data) and tells the owner. The log offers Roll back for a deploy. Deploys are commands (`projects.deploy`, `projects.rollback`), never an agent's call.

**One way to ship.** The ship chore and the captain's lane go through the same rules. A lane call of `tasks.merge`, `tasks.mergeMrs` or `tasks.resolveShip` is checked first by the chore's own readiness checks (committed, merges cleanly, no card waits, no secret in the diff, not a protected repo) and the workspace's allowed branches, then counted in the chore's log under the same key (`ship:<task>:<heads>`), so a state shipped or asked for once is not shipped again, and the daily cap of ships (5, raisable by the owner for a day) counts both. The lane may register a repo under Upkeep (`projects.register`) only when it is one the projects chore would register: unregistered and inside the workspace's folder. Anything else about which repos agents reach stays the owner's.

**The checked hand-off.** When an agent says a task is done (it moves to review), majhi verifies it before the owner or the ship chore sees "Ready to ship" (`apps/server/src/handoff`, captain v2 step 7). Cheap code first: it is committed, it merges into its base cleanly (`git merge-tree` now, not "commits ahead"), no secret in the diff, no card waits, and the project card's lint, build and test commands run in the task's worktree. They run through the same spawner and mounts as the task's own shell (a runner container when there is one, with its memory and process limits), with the shell's environment built from scratch (no account, no connection value, nothing of majhi's own), each with a timeout (10 min tests and build, 5 min lint), and what they print is masked for secrets. A failing test runs once more: a pass on the retry is `flaky`, which is red, not green. A command that does not finish is stopped and reported. A project with no test command says "no test command, not tested" and is not called tested. The brief's checklist items (`- [ ]`) and the bullets under a "Done when" or "Acceptance criteria" heading are each matched to a changed path, an added line or a commit subject, or flagged as having no evidence (a flag is a note: words cannot prove a requirement). The costly part is cached by the task's head commits, so the same head is never run twice; the cheap checks are read live each time, so a conflict that appears after a green check turns it red at once, with nothing run again.

Then a small review, only when the code checks passed. Free checks always run (a TODO added, changed code with no changed test where the project has tests, files outside what the brief names). A diff under 40 changed lines gets nothing more, and a docs-only diff none. A larger one goes to the smallest capable model (the Housekeeper on the cheapest model, no tools), only when Autonomous is on or the owner pressed Check again, never past the monthly ceiling, with a prompt cut to a budget that scales with the diff (6,000 to 24,000 characters of patch, about 700 to 6,200 tokens) and at most six gaps back. Everything from the brief and the diff is fenced as data, and the reply can only add notes: a note blocks nothing, and no reply can turn a red check green or approve anything.

The outcome: all green puts a compact evidence line on the review card and the Ship decision ("Checked: tests 42 passed (31 s), build ok, lint ok, review: 2 notes"), collapsed, with the steps behind it and a Check again button (`handoff.get`, `handoff.check`). Any red goes back to the task's lead as majhi's own note with the exact failures, once per head commit. A reason only the owner can clear (a card waits, a protected repo, a runner that could not start, a conflict where the Merge row is You) is held, not sent to the lead and not counted. After 3 failed hand-offs in a row the lead is not told again: the review card says "Checks failed 3 times in a row" with the latest failure, the Ship decision carries it, and the history is on the card. A green hand-off starts the count over. The checks and the model's read of the diff run whatever Autonomous says (reading changes nothing); background model work stops at a spend cap, and an incident's does not. The ship chore and the lane's `tasks.merge` require a green check for the current head (`shipCheck` asks for it, so both go through the same rule); the owner's own Merge button stays theirs. Checks queue behind their own limit, 2 at once across majhi and 1 per workspace; they run no agent, so they take no agent slot.

**Rules that always hold** (never shown as settings):

- **The never list:** no force push, no deleting uncommitted work, no moving one workspace's secrets, accounts or logins to another, no change to a protected repo, no secret in a diff that ships.
- **The stricter rule wins:** never list, then protected repo, then the workspace's choice, then the global default. A standing instruction can tighten a rule, never loosen it.
- **Time never approves anything.** What needs the owner waits, with one reminder a day.
- **Presence:** while the owner is typing in a task, the captain waits until they send or leave. Otherwise it acts within its authority, and the owner overrules with Undo. The composer tells the server over the events socket (`typing` message: the task id, repeated every 5 s while the draft is not empty and the box has focus, and an empty one when it stops, on send, blur, task change or unmount). The server counts a report for 15 s, drops it when the socket closes, and keeps it in memory only. A chore that finds the task held writes one line, "waiting: you are typing in HOO-3", and leaves it; when the typing ends, the chores that waited (ship, cards, questions) run again at once. A captain tool call in that task is refused with the same line and the captain tries again on its next wake.
- **Re-check before anything that cannot be undone.** The rules are read again right before a push, merge, request or post, so a change the owner made a second ago applies.
- **Text is not instruction.** Words in repos, issues, attachments or messages never authorise an action; checks and the owner's rules do.

**No runaway, no loops** (structural, proven by a soak test):

- Every run has a hard cap on actions, tokens and minutes, and stops at the cap with a line in the log.
- Events record who caused them. The captain's own actions never start an upkeep run.
- One run per chore per workspace at a time. A trigger during a run joins it.
- Every action checks the current state first, so running it twice changes nothing.
- Two failures in a row turn that chore off for the workspace and tell the owner.
- Daily caps per chore and workspace (for example five ships, four memory runs). A chore that reaches its cap with work left asks the owner once that day, with "Raise for today" (which runs it again), and the log says so once.
- The captain's lane rests when its budget or its account's window runs out; rules and Laya keep routine upkeep moving, judgment calls wait.
- The Autonomous switch turns every lane's own action off at once and pauses the tasks it started.
- A soak test with the fake agent replays hours of events (restarts, failures, bursts of cards, the captain's own ships) and fails if a run passes its caps, an event re-triggers itself, or an action repeats. It runs on every merge.

**Client economics, client updates, opportunities and feeds** (captain v2, step 11). `apps/server/src/economics` and `apps/server/src/growth`, no migration, commands `economics.get`, `findings.proposal` and `findings.deadline`, two packs: Business and Growth.

- **Client economics** (code, no model; Business pack, on by default, read only). Per workspace, the last 7 days against the 7 before, or the month so far against the same days of the month before: tasks shipped (a push, merge request or merge in the audit log; a task that pushed and merged counts once), agent minutes (the part of each run inside the period, a run that never closed counting at most 12 hours), spend (all turns of the workspace), and the owner's minutes in reviews and decisions, estimated from what they did (a message to a task at the Answer-a-question minutes, a ship at the Merge minutes, any other approval at the Approve-a-card minutes, all set in the scorecard) and labelled as an estimate. With the retainer the owner entered under Money, the period gets its value (a week is 12/52 of the retainer) and a margin: value less spend, and less the owner's time when an hourly rate is entered. With no retainer there is no margin and no value: nothing is guessed. Flags: spend up by at least a quarter and at least $5 while shipped work grew a quarter less; no shipped work in 14 days in a workspace that has shipped or spent (a workspace that never did anything has no flags); the month's spend at 80 percent of the retainer. The weekly playbook files one `analysis` finding per flag, deduplicated per workspace, flag and week; last week's finding of a flag that still holds is folded into this week's, and one whose flag cleared is fixed. The table is in the Money panel on Health and usage ("Per workspace", Week or Month, with each figure's change and the flags).
- **Client update** (Business pack, weekly on Friday, off by default, per workspace). Code gathers the week: tasks shipped, merge requests, open medium and high risks, incidents, and what is next. A week with nothing shipped and no incident makes no draft and asks no model. The smallest model writes a short update in the workspace's voice profile (the business voice when the workspace has none, plain when neither is set), with the knowledge base entries closest to the week as facts. Voice, knowledge base entries and the week's facts sit in fenced data blocks that stored text cannot close; task titles, commit messages, CRM notes and entries are data. The prompt forbids costs, hours, agents, models, internal ids and invented dates. The result is an email draft through the outbound gate in Draft mode to the CRM contact of the workspace's relation Client tagged `main-contact`. With none, the draft says so at its top, has no address and cannot be sent ("Not sent: the draft has no email address"). No model, a failing model, a reply that is not the JSON asked for, or facts too long for the 6,000 token budget fall back to a plain list written by code, and the run note says which. One draft a week, and none while an earlier one still waits. A draft the gate refuses for holding a secret queues nothing.
- **Opportunities** (Growth pack, weekly on Monday, off by default, a captain playbook). Code collects a brief per workspace: project stacks from the cards, what shipped in 30 days, radar findings, active goals, the knowledge base's products, positioning, pricing and wins, clients and leads, the tasks the owner spent the most actions on, what is listed and what was dismissed, and work built twice inside the workspace (two shipped titles that read alike). The brief goes into the wake as a fenced data block. The captain lists at most five opportunities as findings of source `opportunity`: a one-line pitch as the title, detail that starts with "Effort: small, medium or large", evidence naming what in the brief supports it, and for the single best upsell it may offer a proposal email through the gate. Cost: one short turn (40,000 token budget), and none when the brief has the same facts as the last run that ended well; a failed run is not skipped next week. A reworded pitch that overlaps an existing opportunity of the workspace (even a dismissed one) joins it: the same idea does not come back. "Draft a proposal" on a finding writes a proposal email the same way as the update (voice, knowledge base, template fallback) and queues it to the main contact. Work built twice is looked for inside one workspace only: crossing workspaces would show one client's work in another's lane.
- **Hackathons and grants** (Growth pack, daily, off by default, code, no model). The owner lists feed addresses (RSS, Atom, JSON Feed or a plain JSON list) and the hosts they allow. Only those hosts are reached, on every redirect; a host that is not listed is refused before anything is sent. A host's robots.txt is read (kept a day) and a path it disallows is not fetched; a robots.txt that cannot be read skips the feed. A feed is fetched at most every six hours, with its ETag, reading at most 1 MB. A page, garbage, an oversized answer or a dead host files nothing and says why in the run note. Items match by words from the active goals and the knowledge base (generic words dropped), with words the owner typed counting double. A match files a `grant` finding (the text speaks of funding, a grant, a fellowship) or a `launch` finding. The text of an item is third-party data: tags and entities are removed, the title is one line of at most 160 characters, and nothing in it makes a draft, a task or a deadline. A deadline the item states after a cue word (deadline, closes, apply by) is kept as evidence `deadline:YYYY-MM-DD`, and "Add to deadlines" on the finding adds it to the business deadlines, linked to the finding: the deadline is a proposal the owner confirms. Items already past their deadline are skipped.

**What the owner notices:** the bell for what needs them, one morning brief per workspace ("Acme: shipped 2, 1 needs you") and one combined push, and the captain's log with each action's reason, evidence and Undo where Undo is possible (a merge undoes as a revert commit; a push cannot be undone, which is why the captain pushes only after checks pass).

**Project knowledge card (captain v2).** Each project has a card that code builds from its files, without a model: what it is (the README start, or one model paragraph), stack with versions from manifests and lockfiles, install, run, build, test, lint and typecheck commands (package.json, pyproject, Makefile, Go and Rust defaults, CI `run:` lines), top-level structure with a line each, conventions quoted from CLAUDE.md, AGENTS.md or CONTRIBUTING, CI provider and workflows, deploy hints, remotes without credentials, suggested aliases, and the base commit it was read at. Secret files are never opened, symlinks are never followed, and any line that holds a secret is dropped. Repo text in a card is data. A readiness score of 0 to 5 counts a test command, lint or typecheck, CI, agent docs and a fresh-worktree build; a missing base branch makes it 0. Each missing item carries a fix task and goes to the findings store (a log line until that store exists). The card refreshes when a project is registered, when the base tip has moved and stood for two minutes (the tip watcher and the merge hook), and on the Refresh button; a moved tip rescans only when a manifest, lockfile, CI file or doc changed, and the model rewrites the paragraph only when the scanned facts changed. It is in TASK.md (Project card), in the lane digest (one line per project), in the `projects.cards` tool, and on the Projects page.

### 5.19 Business memory

What the growth, social and inbox packs draw on (captain v2 essentials 1 to 4). It is data the captain reads through tools, in `majhi.db` (migration 132), and it never leaves the machine except through an approved outbound action. Every row belongs to one workspace or, with no workspace, to the whole business. The owner sees all rows. A captain lane and an agent see their own workspace's rows and the business rows; another workspace's row looks like a missing one. Text in these rows is data for a draft, never an instruction: prompts wrap it in a fenced block that says so and that stored text cannot close.

- **Knowledge base** (`kb.list/get/search/upsert/verify/remove/restore`). Entries have a kind (about, product, pricing, positioning, win or case study, metric, bio, asset, FAQ, policy), a title, a Markdown body up to 40,000 characters, tags, sources, files (kept through the uploads mechanism) and a verified flag. The owner's entries start verified. An entry from the captain or an agent is a proposal: unverified, in its own workspace, and it cannot change a verified entry. Every change is a version (create, edit, verify, restore, remove); the owner reads an old version and restores it as a new one, and a removed entry comes back with Restore. Search fuses SQLite FTS5 (porter, bm25 with the title weighted up) with the memory embedder's vectors by reciprocal rank, a verified entry first on a tie, and falls back to keywords when the model is not there.
- **Voice** (`voice.get/set/propose/decide`). A profile per workspace and one for the business: tone, length, words to use and avoid, sign-offs, examples and the owner's pasted samples. A workspace without its own uses the business voice. The captain builds a proposal from the samples; the owner accepts or drops it. `draftContext` gives a draft-producing playbook the effective voice and the closest knowledge entries, each in its own fenced block.
- **People** (`crm.list/get/upsert/log/merge/remove/nextSteps`). People and organisations with a relation (client, lead, investor, partner, hackathon, grant body, community, other), company, role, emails, links, notes, tags, a stage for leads and investors (new, contacted, talking, proposal, won, lost), a next step with a due day, a last touch from the logged interactions, and an owner-only flag that hides the contact from the captain and every agent. The same email or link in the same home is the same contact: a create joins the match, and an edit that makes two contacts share one folds them together. A merge keeps the kept contact's filled fields, joins lists and notes, moves the interactions and reports every field that differed. Error messages name ids, never the data, and nothing here is written to a log.
- **Deadlines** (`deadlines.list/upsert/remove`). Hackathon, grant, launch, client, renewal or other, with a due day or time in the deadline's own time zone, a source, reminder lead days (default 14, 7 and 1, at 09:00 local), and optional links to a goal, a finding and a contact. The list carries the moment in UTC, whole days left, the state in that zone (overdue, today, soon, later, closed) and the next reminder. The agenda reads `deadlines.list` with `withinDays`.
- **Tools.** The reads and the proposals (`kb.upsert`, `voice.propose`, `crm.upsert`, `crm.log`, `deadlines.upsert`) run with no card because the handler ties them to the caller's workspace. Verify, remove, restore, set, decide, merge and delete are the owner's and are not offered as tools.
- **Screen.** Business in the sidebar (`g i`): Knowledge, People, Deadlines and Voice, each with a list on the left (searchable, filtered by workspace, virtualized, keys j and k, `/`, `n`, `e`) and the picked row on the right.

### 5.17 Performance and resource use

- **Worktree budget.** At most `limits.worktrees` task folders (default 15; majhi.yaml, live-editable). Over it, when a task closes and when one starts running, the oldest done, reviewed or paused task folder goes whole after its branch is saved (its worktree is clean, even of untracked files, and its tip is merged into the base or pushed): its worktrees are removed through git, the folder is emptied and the report (`REPORT.md`) stays. A running task, a task the owner pinned (`tasks.pin`, owner only) and a folder with a change that is not committed are never removed; the report says why. Archive on merge: a task that closes merged loses its folder at once; its room, report and branch history stay.
- **Package stores.** One per workspace (`<majhi home>/cache/<org>`, mounted into that workspace's runs only). Measured on OrbStack and Docker's bind mounts: two mounts never share a hard link (`EXDEV`), and a link into any path with a `node_modules` component on a host bind mount is made as a copy, so pnpm's link count stays 1 on this runtime whatever the layout; a named volume hard-links (22 of 23 files). The copy costs next to nothing on disk there (the host's free space moved 1 MB for a 43 MB `node_modules`), so the disk win comes from the shared builder, the project environment and the budget instead (docs/DECISIONS.md, 2026-10-19).
- **Task disk use.** Cleanup includes wholly ignored dependency and tool caches, including `node_modules` and `.pnpm-store`. An explicit cache-only preview and run can free these in any done task without waiting for source retention. This preserves dirty worktrees, task branches and room history. Never follow cache symlinks, remove tracked files, or reclaim dependencies from an unfinished task. Normal worktree and history cleanup still follows `cleanup.after_days`.
- **Backup scratch.** Backup operations serialize cleanup of crash-left database copies before making another archive. Saved archives and pending restore staging stay protected.
- **Agents on demand.** Agent processes start when a run needs them and stop after `idle_timeout` (default 3 minutes; the runner container goes with the process). Sessions come back with ACP `session/resume` or `session/load`.
- **Concurrency limits.** A global maximum of running agent processes (`agents_max`, default 6), a maximum per account, and a maximum per task. Extra runs wait in the jobs table and show as queued, with their place in line.
- **Budgets.** Optional token or cost budgets per account, org and task, per day. At the budget, runs pause with reason `limit`. The owner or the captain can raise them.
- **Models load lazily.** Laya and the embedding model load on first use and unload after idle. Docker memory limits cap each service.
- **Server.** SQLite in WAL mode with prepared statements, bounded caches, streaming with backpressure, repo scans cached and refreshed by file watchers. The UI pages and virtualizes long rooms and lists.
- **Configurable.** Every limit lives in `majhi.yaml` under `limits` and can be changed live, by hand, in Studio, or by the captain.
- **Targets**, measured in Phase 9: task switch under 100 ms, room updates on screen under 50 ms after the server receives them, server memory under 200 MB with no agents running.

### 5.20 Backups and restore

Everything majhi cannot rebuild is backed up as one encrypted archive: the SQLite databases (`majhi.db` with tasks, rooms, decisions and labels, findings, captain state, project cards and whatever tables come later; `memory/memory.db`), the config folder's history (a git bundle) with its visible files (`majhi.yaml`, agents, skills), and `secrets.age` exactly as it is on disk. Never in an archive: the secrets key or any age identity (files holding one are skipped), account logins and agent homes, connection credentials, caches, task folders and worktrees. The manifest says so.

- **Consistent copies.** Databases are copied with SQLite's online backup API, never by copying a live WAL file, and each copy passes `quick_check` before it is packed. The archive is tar, gzip level 3, then age, streamed to `<name>.part` and renamed after fsync, so a full disk or a crash leaves no file that looks like a backup. The manifest holds the majhi version and commit, each database's newest migration id and a SHA-256 for every file.
- **Locks.** Archives are encrypted to the secrets key, so the key (Keychain copy or passphrase export) is what opens them. "Back up with a passphrase" makes one locked with a passphrase the owner types; majhi never keeps it.
- **When.** Daily (the first check 30 s after start, then hourly, catching up after sleep), before every `system.update` (skipped when a backup under 5 minutes old exists), before any migration (at start, before a database is opened, when it is behind this build), before a restore, and on request (`backup.now`).
- **Where.** `<majhi home>/backups` by default, or any folder the owner picks with the host helper's folder browser (`backup.setDestination`), for example an iCloud or Dropbox folder. Inside the server container a folder must be covered by a bind mount, or majhi refuses it: otherwise the archives would vanish with the container. A folder inside the majhi home is refused.
- **Retention.** The newest 7 daily backups, the newest daily one of each of the 4 weeks before them, and the newest 3 of each other kind. A backup that failed its check takes no slot and goes once a good one is kept. The newest good backup is never deleted, whatever the rules say.
- **Test restore.** `backup.verify` restores a backup into a temporary folder, checks every file against the manifest, opens both databases read-only, runs `integrity_check`, compares each migration id with this build's, and rebuilds the config history from the bundle. Nothing live is touched. majhi runs it weekly on the newest key-locked backup. The result shows in Hub setup, Backups, and as the Health checks "Backups" and "Backup test restore". A backup that cannot be opened with this computer's key is "locked", not "damaged".
- **Restore.** `backup.restore { name }` (owner only, destructive): check the backup as above in `restore-staging/<id>`, take a `before-restore` backup of what is there, write `restore-journal.json`, and restart majhi (under docker compose the container restarts itself). At the start of the next process, before any file opens, each replaced path (databases with their `-wal` and `-shm`, `memory/memory.db`, `secrets.age`, `.git`, `majhi.yaml`, `agents/`, `skills/` and the other visible config files) moves to `rollback/<id>/` and the verified copy takes its place. Any failure, or a start that finds a swap that never finished, moves everything back and records why. A backup whose `secrets.age` the current key cannot open keeps the live secrets file. A backup from a newer migration than the code knows is refused. The two newest rollbacks are kept.
- **UI.** Hub setup, Backups: last backup and size, next daily, folder (Change), test restore result, Back up now, Test restore, and a list with Test and Restore per row. Restore confirms with the list of what is replaced.

### 5.21 The wiki and chat diagrams

A wiki per project that says, in plain words and with a file and line behind every claim, where the frontend, backend, workers, queue, cache, database and sign-in are, where requests and jobs start and how each main flow moves through the pieces, and what is proven, what is guessed and what could not be worked out. The owner reads it in the app and agents read it at the start of every task. The design and the measurements behind it are in `docs/design/wiki.md`. The same drawing tool serves any agent in any chat. It replaces the Map, its Inside tab, Journeys and `show_map`, which are removed.

- **The switch.** `wiki.enabled` in `majhi.yaml` (default off) and `orgs.<id>.wiki.enabled` per workspace (Default, On or Off). One function, `wikiEnabled(org)`, reads the workspace value over the global one on every call, so a change applies at once. Off means nothing runs, no `wiki` tool is offered, TASK.md has no wiki section, the memory brief keeps its Architecture section, and there is no sidebar entry. Pages and state stay, so turning it on again is instant. The switch is in Settings, Agents, Wiki (with majhi's writer model) and in each workspace's settings.
- **Facts first, the model writes last.** Tools find facts with evidence and the model only names, groups and words them. It cannot invent a component or a link. Every claim cites `{repo, commit, path, lines, hash}`, and a checker drops any claim whose citation does not hold.
- **Facts** (no model, per project). A clean `git archive` of the commit the wiki is built from is unpacked to `<tasks folder>/.wiki/<workspace>/<project>/src-<commit>/` and read, never the checkout, so agent worktrees and uncommitted edits never leak in. The sealed reader (the throwaway runner container with no network, a read-only root, the export mounted read-only and one writable cache folder; `docker/wiki_facts.py`) finds HTTP routes with OWASP Noir (`v1.4.0`, pinned in the runner image; route paths, never values, may leave it), and queue consumers, timers, commands and sockets with the entry pass of `docker/map_inside.py`, Celery beat schedules and cron fields, and HTTP client calls (`docker/wiki_calls.py`), then runs graphify (`graphifyy==0.9.77`) for the code graph. The graph keeps `graph.json` and its state in `.wiki/<workspace>/<project>/graph/` and is rebuilt by content, so an unchanged tree reads in under a second. On the server, scanners read every compose file (found by name), Kubernetes and Helm file (found by content), package and Python manifest, Dockerfile, `.env.example` and deploy file (Vercel, Netlify, Fly, Render, Heroku, Cloudflare) of every workspace member, through `ProjectFiles`, which refuses `..`, absolute paths, symlinks out of the export and files over 256 KB. Roles come from a typed catalog (`wiki/facts/known.ts`: a framework, a datastore driver or image, a sign-in or token library, an SDK, a proxy image), never from the model, and a role with nothing behind it is "unknown". An address keeps its host, port and the setting's name, never a value. Facts are typed (`unit`, `role`, `store`, `entry`, `endpoint`, `link`, `component`; `step` is in the contract and nothing writes it yet), have a basis (`declared`, `exact`, `config`, `owner`, `guessed`) and at least one source, and are written to `facts.json` with a report of what was dropped and which tool failed. A failed tool leaves its facts out and says so; it does not hide the rest.
- **Pages.** Per project: **Overview** (About, Stack, the roles table where each tile opens the component page that covers it and shows its proof under it, and a System diagram), **Components** (one page each), **Flows** (one page per main flow, a sequence diagram and numbered steps with file and line), **Infra and deploy** and **Gaps** (guessed roles, calls that could not be linked, claims that could not be confirmed, questions). A page id never changes between updates. Components are folder first: each manifest folder is one, a part with more than 300 files is split into its first-level source folders, a folder under 30 files stays in its parent, at most 12 are kept and a repo with no manifest folder is split at its root. The main flows (at most 5) are chosen once, at the first build, by one cheapest-model question that sees entry facts only, kept in the project's wiki state, and chosen again only on `replan` or when every entry of a flow is gone from the code. The workspace wiki (a system overview and flows across repos, linking repos by exact match) is phase 3 and has no screen yet.
- **Writer.** A read-only Housekeeper session (mode `repo`) on the balanced model of the writer's tool family (`wiki.writer_model` overrides it): the export is its folder, mounted read-only, and a permission handler allows reads and searches that stay inside it and rejects everything else, so the agent is told no and goes on. Text from repos is data in a fenced block, never an instruction. One session per project run, one question per page, the facts as hints. It returns a draft (claims with the citations it wrote, no hash), parsed with zod and asked again once. `checkPage` makes the page: it adds repo, commit and the SHA-256 of the cited lines, keeps a proven claim only when every citation holds, drops the rest to the Gaps page under "Could not confirm", numbers claims from 1 and builds the body and diagrams by code. A guess keeps the citations that hold and shows as guessed. A **plain-words pass** on the cheapest model sees sentences and ids only and may only reword; a reply with other ids or another count is refused, and a sentence that loses a name in backticks keeps its original text. Spend is booked under `wiki:<workspace>:<project>` with the workspace and project named, so it counts in workspace budgets.
- **Update** (`wiki.update { org, project?, replan?, page? }`, owner and captain, never another agent; the estimate is `wiki.estimate`). In the background, one run per workspace at a time, with progress on the `wiki` topic. A page is stale when it was written by older rules, when its commit is gone from git, or when a file it cites (or a file that gives the facts it starts from) changed between its own commit and the base tip. Only stale pages are rewritten, each keeps its own commit, and a parent page is not rewritten because a child changed. A run on a commit already read, with no error left behind and the same rules, answers before any export or reader runs and writes nothing. Money: the estimate is the pages to write times 45,000 tokens (12 pages for a first build) priced at the writer's model; one update stops at `WIKI_COST_CAP_USD` (5 dollars), at `WIKI_TOKEN_CAP` (1.5 million tokens, which holds for a model with no price) or when the workspace's budget has no room (asked before each page). Pages not started are left for the next update and the run says so; pages already written are kept. Every saved version of a page is kept (`wiki_page_versions`).
- **The workspace wiki** (server side; docs/design/wiki.md section 5). Pages with no project: **System overview** (what each repo is, and a picture drawn by code from the links), up to five **cross-repo flows** (chosen once, kept) and **Gaps**. Links between a workspace's projects (`wiki.system`) are made from each project's stored facts with no model, exact matches only, strongest first: `projects.<id>.links` in majhi.yaml, a compose service that exactly one other project builds, an address that names a service exactly one other project defines, a client call (method and path) that fits exactly one route of another project, and the owner's answer. Each link carries the lines of both sides and its basis. Calls that fit nothing are listed as "Not linked calls" with `path:line` (on the project's Gaps page and the workspace's), and addresses nobody placed are questions for the owner. The owner answers with `wiki.answer { org, question, to }` (a project of that workspace, outside, ignore, or null to forget): the links and the Gaps pages are drawn again at once with no model, and every later update applies the answer (table `wiki_answers`). `wiki.setRole { org, project, role, where, choice }` confirms or changes a role the writer guessed (applied on read, kept across updates). The writer is the Housekeeper in read-only mode with every project's export mounted; a claim cites `{repo, path, lines}` and each citation is checked in the export of its own repo only. A project update makes stale only the workspace pages that cite that project. The `wiki` tool lists and reads the workspace pages (`workspace: true`), and TASK.md has one line on the links that touch the task's repos.
- **Fresh.** `ProjectCards` already notices that a base tip moved and has stood; it tells the wiki, which emits the `wiki` topic so the page's behind lamp moves. There is no second watcher. With Autonomous on, the captain's **Wiki** chore (an upkeep chore, the playbook `upkeep-wiki`, daily) runs the same update for a workspace whose wiki is on and for projects that were built and are behind, within the workspace's budget, with the action key `wiki:update:<workspace>:<day>`. A project never built waits for the owner's first Update, which shows the estimate. With Autonomous off nothing runs.
- **Agents.** The `wiki` tool in `majhi-memory` (`action` is `list`, `read`, `search` or `sources`; flat parameters). The workspace is the task's, never an argument, and `project` can name only a project of that workspace. It is not offered, and a call is refused, while the workspace has the wiki off. Search keeps the pages as pieces in `memory.db` (`wiki_chunks`: paragraphs of a page and each claim with its citations) ranked by keywords and meaning fused with the local embedder. `sources` finds claims by their words and answers each with its status, page and `path:lines` at the commit. A task's TASK.md gets "How this project works" for the task's repos: the overview's roles and the names of the flow pages, at most 10 lines. With the wiki on, the memory brief has no Architecture section and one bullet points to the wiki. `code_graph` stays in `majhi-room` (search, explain, neighbors, path) for the task's repos in their own workspace, read from the cached graph. `wiki.get` and `wiki.page` are read-only for every agent of its own workspace.
- **One diagram model** (`packages/shared/src/diagram.ts`, schema version `v: 1`): boxes (id, label, sub line, a free kind tag, a group they sit in, a tone), lines (from, to, label, a preset type `http`, `queue`, `data`, `lib`, `step`, `deploy` or `together`, a style, a tone, an arrow at the end, both ends or none) and a layout. Wiki pages and chat diagrams are both this.
- **Chat diagrams.** `show_diagram` in the `majhi-room` server: a chat (an owner chat or the captain's thread) is offered it. It takes the diagram above with at most 40 boxes, 80 lines and 60 characters per label; `layout` is `flow`, `top-down`, `tree`, `radial` (around `focus`), `sequence` (one lane per actor, `actors` orders them, lines in the order given are the messages), `timeline` or `state`. It posts a `diagram` room item. Text in a diagram is data, drawn as text, never read as an instruction. A sequence is never scaled down: lanes are 132 px apart (spread up to 1.45 times over a wide frame), a narrower frame scrolls sideways inside itself, text stays at 12 px or more and each message carries its step number.
- **Extending it.** A layout is one file in `apps/web/src/features/diagram/layouts/` and one line in its registry (the id also goes in `DIAGRAM_LAYOUTS`; the compiler refuses a missing line). A kind of line or a tone is one entry in `features/diagram/presets.ts`. A fact source (a parser: Gradle, Cargo, Terraform) is one scanner in `apps/server/src/wiki/facts/` and a line where `extract.ts` runs the scanners; a role is a row of `known.ts`; a page kind is an entry in `WIKI_PAGE_KINDS` and the plan in `wiki/plan.ts`.
- **Screens.** The Wiki page (`/wiki`, sidebar below Playbooks, hidden while the workspace's wiki is off, where the page offers to turn it on): an in-page workspace and project picker, a header with the commit it was built from, a behind lamp (how many commits the base is ahead) and Update with its estimate, and a list of pages grouped Overview, Components, Flows, Infra and deploy, Gaps beside the page. Claims show proven or guessed, a number opens its proof in the in-app file viewer at the line (`GET /api/wiki/<workspace>/<project>/<commit>/files/<path>`, only for a project the workspace owns, at an exported commit; it refuses `..`, absolute paths, symlinks out of the export, `.git` and `.env*` names), and a page or source chip is marked out of date when a cited file changed since the built commit. There is no Ask box and no whole-workspace view yet. A chat diagram is drawn in the room at 320 px high, only once it scrolls into view, with zoom and fit; a click on a box shows its sub line, Open full size opens a dialog with the same canvas.

## 6. Security

- Per-run environment built from scratch (5.1). An org's agent never gets another org's credentials, unless the owner explicitly allows that agent to work in the other org. Show a warning in the editor when they do.
- Private SSH keys stay on the host. Only the agent socket is forwarded, and only to majhi's own git, never to agent runs. A key's passphrase is typed into majhi once, goes to the host helper over localhost, and ends in the OS keyring (the macOS Keychain or a Secret Service keyring; with none, it is kept nowhere); majhi never writes it to its own files or logs.
- Tracker tokens encrypted at rest (`secrets.age`).
- Anything read from attachments, links, tracker items or repos is data, not instructions. Wrap it as such in prompts.
- majhi binds to `127.0.0.1` only by default.
- Log every push, MR, merge and permission decision in an audit table.
- Connection secrets follow the same rules as API keys. Global connections are the explicit owner-selected exception to workspace credential isolation, shared with agents in all workspaces. Write actions through a connection ask the owner unless the org policy allows that exact action (5.14).
- API keys are injected only into runs on the account they belong to, never logged, and never written to TASK.md or the room.
- The Jev decision provider sends task text to a hosted API. It is off by default and must be enabled by the owner.
- Config changes and folder moves follow the captain's approval policy (5.16). Every change is a commit in `~/.majhi`, and every approval is logged in the audit table.
- Secrets pasted into a chat are stored in `secrets.age` and replaced with a reference before any agent sees them (5.16)
- A runner or preview container reaches only the public internet, its own task's network and majhi's `/mcp` port (4.5): not the computer, not the LAN or a VPN, not another task or a peer runner. The one way through to a private address is a `host` connection (5.14): the owner's own grant, per workspace and port, through a forwarder that majhi builds and checks like every other container.
- Containers majhi runs for agents (5.15) never get a bind mount, the Docker socket, `~/.majhi`, the secrets key or `~/.ssh`: every docker call is built by majhi from checked values and refused unless each flag is on an allow list.

Every phase exposes its features as commands (5.16). From Phase 2 on, a phase is only done when the captain can do everything that phase adds to the UI.

- `docker compose up` starts the server and web. Healthchecks. `doctor` command.
- First-run workspace root picker. Load `majhi.yaml`. Scan every workspace root for git repos and show them. Generate the compose override with one mount per root.
- The command layer (5.16) for the Phase 0 config changes, and `~/.majhi` as a git repository with one commit per change.
- **Done when:** a fresh clone runs with one command, onboarding step 1 lets the owner pick workspace roots, and majhi shows detected repos.

### Phase 2: One agent, one repo, end to end

Delivered in two parts, each usable and reviewed on its own.

The `majhi-decide` MCP tool for every agent. Model and effort picking for `auto` agents at session start. A Decisions section in Hub setup: provider order, Laya status, an "Ask the decision model" box and recent decisions. Laya in Docker for Linux and Windows comes later.
